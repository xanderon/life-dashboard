Node.js: Process vs Thread vs Event Loop vs Workers

Node.js Event Loop Process vs Thread libuv Thread Pool Worker Threads Interview Prep

Pagina asta rezumă clar discuția din chat: ce este un proces, ce este un thread, cum se leagă asta de Node.js single-threaded, ce face event loop-ul, ce înseamnă libuv thread pool, când apar worker threads și de ce la microservicii auzi de multe ori de workers cu sensuri diferite.

Definiția / Problem Statement

Întrebarea centrală

Într-un microserviciu Node.js, dacă limbajul e “single-threaded”, atunci: ce este procesul?, ce este thread-ul?, cine face I/O?, ce face event loop-ul? și ce înseamnă workerii despre care vorbim în sistemele reale?

Definiție scurtă

Proces = instanța unei aplicații care rulează, cu memorie proprie.

Thread = fir de execuție din interiorul unui proces.

Pentru Node.js

Un proces Node.js are de regulă un thread principal JavaScript, pe care rulează event loop-ul, plus alte thread-uri folosite în fundal de runtime pentru anumite operații.

Intuiția corectă

Ideea mare: Node.js nu înseamnă “un singur lucru se întâmplă în tot procesul”. Înseamnă că codul tău JavaScript rulează în mod normal pe un singur thread principal. Dar operațiile de I/O sau unele task-uri speciale pot fi făcute în fundal, iar când sunt gata, rezultatul revine înapoi la event loop.
Confuzia clasică

Request-ul HTTP nu este un thread. Nici un listener, nici un for, nici un callback nu sunt thread-uri.

Ele sunt bucăți de cod care sunt executate de thread-ul principal sau sunt reluate de acesta când operația async asociată s-a terminat.

Mental Model

1. Pornești microserviciul Node.js → ai un proces.
2. În acel proces există un thread principal care execută JavaScript.
3. Event loop-ul rulează pe acest thread principal și orchestrează execuția.
4. Dacă faci operații async, Node.js le poate delega către OS/libuv.
5. Când rezultatul e gata, callback-ul / promise continuation se pune în coadă.
6. Event loop-ul ia acea sarcină și o execută tot pe thread-ul principal.

Comparație rapidă

Concept Ce este În microserviciul tău Node.js
Proces Instanță de aplicație cu memorie proprie Microserviciul pornit în runtime
Thread principal Firul pe care rulează JS Aici rulează handler-ele, callback-urile, promise-urile
Event loop Mecanism de orchestration Ia task-uri gata și le execută pe thread-ul principal
libuv thread pool Thread-uri de fundal pentru anumite operații Folosit automat pentru unele task-uri precum fs/crypto/dns

Step-by-step: ce se întâmplă la o operație async

Exemplu: primești un request și scrii pe disc
  1. Intră request-ul HTTP în microserviciu.
  2. Handler-ul tău rulează pe thread-ul principal.
  3. Apelezi ceva async, de exemplu fs.promises.writeFile(...).
  4. Node.js nu blochează thread-ul principal așteptând rezultatul.
  5. Operația este delegată în fundal.
  6. Thread-ul principal poate continua cu alte evenimente.
  7. Când scrierea s-a terminat, event loop-ul primește faptul că operația e gata.
  8. Continuarea promise-ului tău se execută pe thread-ul principal.

Event Loop: ce face de fapt

Pe înțeles simplu

Event loop-ul nu execută totul în paralel pe thread-ul principal. El rulează pe rând task-urile care au devenit gata.

Deci da: event loop-ul gestionează efectiv un task JavaScript la un moment dat pe thread-ul principal. Dar între timp, alte operații async pot progresa în fundal.

Formulare bună de interviu

„Event loop-ul nu face munca grea de I/O în sine. El orchestrează fluxul: pornește operații async, apoi, când acestea se termină, execută callback-urile sau continuările promise pe thread-ul principal.”

Ce merge automat în fundal în Node.js

Fără să creezi tu manual thread-uri, Node.js poate folosi infrastructura din spate pentru anumite operații. Pentru interviu, ideea importantă este:

  • Operațiile de rețea nu blochează thread-ul principal.
  • Operațiile pe fișiere async sunt gestionate în fundal.
  • Unele operații crypto / dns folosesc thread pool-ul din libuv.
  • Codul tău JavaScript nu este automat mutat pe alt thread doar pentru că e lent.
Foarte important

Dacă scrii cod CPU-bound sincron în JavaScript, de exemplu un calcul mare sau un loop greu, atunci blochezi thread-ul principal. Event loop-ul nu mai poate servi alte request-uri până nu termini.

Thread Pool-ul din libuv

Pe scurt: există un thread pool folosit de runtime pentru anumite categorii de operații. Implicit, dimensiunea lui este adesea 4, iar o poți influența prin UV_THREADPOOL_SIZE. 
// exemplu de setare înainte să pornești aplicația
// macOS / Linux:
UV_THREADPOOL_SIZE=8 node app.js

// Windows PowerShell:
$env:UV_THREADPOOL_SIZE=8; node app.js
Ce să ții minte

Asta nu înseamnă că tot codul tău JavaScript începe să ruleze în 8 thread-uri. Înseamnă doar că anumite task-uri delegate în fundal pot avea mai multă capacitate.

Worker Threads vs “workers” în sens de aplicație

1) Worker Threads

Sunt thread-uri reale create explicit cu modulul worker_threads. Le folosești când vrei să rulezi cod JavaScript CPU-bound separat de thread-ul principal.

2) Workers de business

În multe echipe, „worker” poate însemna un consumer RabbitMQ, un job executor, un process separat sau o replică de microserviciu. Nu înseamnă automat worker_threads.

Capcana de vocabular

Dacă cineva din echipă spune „avem 20 de workers”, nu presupune imediat că sunt 20 de worker threads. Pot fi:

  • 20 consumers logici pe o coadă
  • 20 procese separate
  • 20 pod-uri / replici
  • 20 task-uri concurente controlate în aplicație

Exemple de cod

1. I/O async normal în Node.js

const fs = require('fs/promises');

async function saveLog() {
  console.log('start');

  await fs.writeFile('./app.log', 'hello world');

  console.log('file written');
}

saveLog();
Cum îl explici

saveLog pornește pe thread-ul principal. Când ajunge la await fs.writeFile(...), operația de scriere este delegată în fundal. Thread-ul principal nu stă blocat să aștepte fizic scrierea. Când operația s-a terminat, continuarea după await revine în event loop și se execută pe thread-ul principal.

2. CPU-bound care blochează event loop-ul

function heavyCalculation() {
  let sum = 0;

  for (let i = 0; i < 2_000_000_000; i++) {
    sum += i;
  }

  return sum;
}

console.log('before');
const result = heavyCalculation();
console.log('after', result);
Problema

Aici nu e I/O async. E calcul sincron greu în JavaScript. Totul rulează pe thread-ul principal și blochează event loop-ul.

3. Worker thread explicit

// main.js
const { Worker } = require('worker_threads');

function runWorker(data) {
  return new Promise((resolve, reject) => {
    const worker = new Worker('./worker.js', { workerData: data });

    worker.on('message', resolve);
    worker.on('error', reject);
    worker.on('exit', (code) => {
      if (code !== 0) reject(new Error(`Worker stopped with code ${code}`));
    });
  });
}

(async () => {
  const result = await runWorker({ n: 5_000_000 });
  console.log('worker result:', result);
})();
// worker.js
const { parentPort, workerData } = require('worker_threads');

let sum = 0;
for (let i = 0; i < workerData.n; i++) {
  sum += i;
}

parentPort.postMessage(sum);
Ideea

Aici ai creat explicit un worker thread. Asta e altceva decât I/O-ul async normal. Folosești această abordare când vrei să muți calcule grele în afara thread-ului principal.

Unde apar conflictele?

Răspuns nuanțat

Dacă rămâi doar pe modelul clasic Node.js, mult cod JS se execută secvențial pe thread-ul principal, deci nu ai aceleași conflicte de memorie ca în multe modele multi-threaded tradiționale.

Dar poți avea în continuare:

  • race conditions de business între request-uri sau job-uri async
  • conflicte la nivel de DB / queue / state extern
  • probleme reale de shared memory dacă folosești worker threads cu memorie partajată
Exemplu din viața reală

Două mesaje RabbitMQ pot încerca aproape simultan să proceseze același device. Chiar dacă JS rulează pe un thread principal, operațiile async pot interfera logic. De aceea apar lock-uri, idempotency, prefetch, batch-uri și controale de concurență.

Real-world use cases

HTTP server clasic

Request-urile vin, handler-ele rulează pe thread-ul principal, I/O-ul se face non-blocking.

RabbitMQ consumer

Poți avea mai multe mesaje în procesare, dar trebuie controlată concurența și ordinea.

File system / logs / uploads

Operațiile pe fișiere async nu ar trebui să blocheze event loop-ul.

CPU-heavy processing

Aici intră în scenă worker threads sau alt proces / alt serviciu.

Common mistakes / confusions

  • Să spui că fiecare request HTTP este un thread.
  • Să spui că event loop-ul face munca de I/O.
  • Să crezi că single-threaded înseamnă zero concurență.
  • Să confunzi worker threads cu workers ca termeni de business.
  • Să crezi că mărirea lui UV_THREADPOOL_SIZE accelerează orice cod lent.
  • Să uiți că task-urile CPU-bound în JS blochează event loop-ul.

Interview explanation version

„În Node.js, microserviciul meu rulează ca un proces. În acel proces am, în mod normal, un thread principal pe care rulează JavaScript și event loop-ul. Event loop-ul nu execută I/O-ul în sine, ci orchestrează lucrurile: pornește operațiile async, iar când ele sunt gata, execută callback-urile sau continuările promise pe thread-ul principal. Pentru anumite operații, Node folosește infrastructură de fundal, inclusiv libuv thread pool. Dacă am workload CPU-bound, atunci folosesc explicit worker threads sau mut logica într-un alt proces ori serviciu. Iar când echipa spune ‘workers’, poate însemna fie worker threads, fie consumers sau executori logici, nu neapărat thread-uri reale.”

Pattern to remember

Formula scurtă

Process = containerul mare al aplicației.
Thread principal = unde rulează JS.
Event loop = orchestratorul.
Async I/O = progres în fundal fără blocare.
Worker thread = thread explicit pentru task-uri grele.

Final explanation

Da, ai gândit bine în chat: microserviciul poate fi privit ca procesul. Dar „thread-ul” nu este un request sau un event listener. Thread-ul este unitatea de execuție de la nivel de runtime / OS. În Node.js, codul tău JS rulează în principal pe un singur thread, iar event loop-ul îl ține ocupat cu task-urile gata de rulat.

Când faci I/O async, Node nu blochează acel thread: delegă operația și revine la alte lucruri. Când operația s-a terminat, rezultatul se întoarce și este procesat de event loop. Dacă ai nevoie de paralelism real pentru calcule grele, intri în zona de worker threads sau procese separate.

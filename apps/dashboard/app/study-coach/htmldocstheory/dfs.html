Definition

Simple definition

DFS (Depth-First Search) is a traversal algorithm for graphs or trees that goes as deep as possible on one path before coming back and trying another path.

In practice, DFS is driven by a stack — either an explicit stack in code or the language's call stack when using recursion.

The core intuition

Mental model

Think of exploring a cave or maze. You pick one tunnel, keep going until you hit a dead end, then backtrack and try the next tunnel.

Why it exists

When a structure branches, you need a systematic way to visit all reachable nodes. DFS gives you a disciplined "go deep, then come back" strategy.

Start | A | B | C | D Go deep → hit dead end → backtrack → explore another branch

DFS vs BFS — the interview-friendly explanation

Good interview explanation:
DFS and BFS are both traversal algorithms for graphs or trees. BFS explores level by level using a queue (FIFO), while DFS explores as deep as possible using a stack (LIFO) or recursion. Conceptually, they are very similar — the big difference is the data structure that controls the order of exploration.

BFS

  • Uses a queue
  • FIFO behavior
  • Explores level by level
  • Best when you need shortest path in an unweighted graph

DFS

  • Uses a stack
  • LIFO behavior
  • Explores one path deeply first
  • Great for traversal, backtracking, cycle detection, components
Important interview nuance

Do not say "DFS = recursion". That is incomplete. The correct idea is: DFS is a traversal strategy based on stack behavior. Recursion is just one way to implement that stack behavior.

Visual intuition

A / \ B C / \ \ D E F Possible DFS order: A → B → D → E → C → F
Why that order?

DFS picks one branch and keeps going until it cannot continue. Only then does it return and explore remaining branches.

Backtracking

Backtracking is not something extra added later. It is built into DFS: when you finish a branch, you naturally return to the previous node.

Iterative DFS is basically BFS with a different container

This was one of the key insights from the discussion: yes, DFS can be implemented almost exactly like BFS, as long as you change the data structure from a queue to a stack. 

// BFS
function bfs(graph, start) {
  const visited = new Set();
  const queue = [start];

  while (queue.length) {
    const node = queue.shift();

    if (visited.has(node)) continue;
    visited.add(node);

    for (const neighbor of graph[node]) {
      queue.push(neighbor);
    }
  }
}
// DFS (iterative)
function dfs(graph, start) {
  const visited = new Set();
  const stack = [start];

  while (stack.length) {
    const node = stack.pop();

    if (visited.has(node)) continue;
    visited.add(node);

    for (const neighbor of graph[node]) {
      stack.push(neighbor);
    }
  }
}
Key takeaway

The code shape is very similar. The real difference is: queue.shift() for BFS vs stack.pop() for DFS.

Step-by-step example

A | \ B C | D

Start

stack = [A]

visited = {}

We begin with the start node on the stack.

Pop A

Visit A, mark it visited, push its neighbors.

stack = [B, C] or similar depending on push order.

The stack controls which branch goes next.

Pop top element

Because this is LIFO, the most recently added neighbor is explored first.

This is why DFS order can vary depending on neighbor ordering.

Keep going deep

Each time you pop a node, you visit it and push its unvisited neighbors.

That creates the "go deep first" behavior.

Backtrack naturally

When a node has no new neighbors, the algorithm just keeps popping older nodes.

That automatic return is the essence of backtracking in DFS.

Recursive DFS

Recursive DFS is often simpler to write because the language stack behaves like the DFS stack. 

function dfs(node, graph, visited) {
  if (visited.has(node)) return;

  visited.add(node);

  for (const neighbor of graph[node]) {
    dfs(neighbor, graph, visited);
  }
}
Conceptual translation

Each recursive call means "go one level deeper". When that call finishes, execution returns to the caller — that return is backtracking.

Complexity

Time complexity

O(V + E)

You visit each vertex at most once and inspect each edge at most once.

Space complexity

O(V)

For the visited set and for the stack / recursion depth in the worst case.

Why grid DFS feels much easier than graph DFS

General graph

In a general graph, you must explicitly store the neighbors, usually using an adjacency list like { A: ['B', 'C'] }.

Grid

In a grid, neighbors are implicit. From (r, c), you can derive neighbors mathematically: (r+1,c), (r-1,c), (r,c+1), (r,c-1).

Why interviewers love grid DFS

Grid problems are easier to set up, easier to visualize, and they test the same core skills: recursion, boundary checks, visited marking, connected components, and complexity reasoning.

Reusable grid DFS template

One big reason grid DFS is common in interviews is that the template is almost reusable across many problems. 

function dfs(grid, r, c) {
  const rows = grid.length;
  const cols = grid[0].length;

  if (
    r < 0 ||
    c < 0 ||
    r >= rows ||
    c >= cols ||
    grid[r][c] === 0
  ) {
    return;
  }

  // mark visited
  grid[r][c] = 0;

  dfs(grid, r + 1, c);
  dfs(grid, r - 1, c);
  dfs(grid, r, c + 1);
  dfs(grid, r, c - 1);
}
Pattern to remember

Most grid DFS problems are some version of: boundary check → invalid cell check → mark visited → explore neighbors.

Line-by-line explanation of the grid template

Boundary checks

Stop if the cell is outside the matrix. This prevents invalid memory access and infinite wandering.

Invalid-cell check

Stop if the current cell is not part of the structure you care about (for example water instead of land, or already visited instead of fresh).

Mark visited

This is essential. Without it, you can revisit the same cell forever. In grid problems, people often mutate the grid itself instead of using a separate visited set.

Explore neighbors

The recursive calls implement the actual DFS expansion: down, up, right, left — or whatever direction list the problem requires.

Common mistakes / confusions

  • Confusing DFS with recursion. DFS can be recursive or iterative.
  • Forgetting the visited check. This can cause infinite loops in graphs with cycles.
  • Forgetting boundary checks in grids. This causes index errors.
  • Thinking DFS always gives shortest path. It does not. BFS does for unweighted graphs.
  • Ignoring neighbor order. DFS order depends on the order in which neighbors are pushed.
  • Recursive stack overflow. On very deep inputs, iterative DFS may be safer.

Real-world use cases

Backend / systems
  • Dependency exploration
  • Cycle detection in dependency graphs
  • Configuration tree traversal
  • File system traversal
Apps / algorithms
  • Maze solving / path exploration
  • Connected component detection
  • Flood fill / image region detection
  • Backtracking problems like combinations or permutations

Brute force comparison

Without DFS

You would often end up manually exploring paths, duplicating checks, and risking missed nodes or repeated work.

With DFS

You get a reusable traversal strategy: choose a node, mark it, recursively or iteratively explore reachable neighbors, and let the algorithm systematically cover the structure.

Interview explanation version

30-second answer:
DFS, or Depth-First Search, is a traversal algorithm for graphs and trees that explores one path as deeply as possible before backtracking. It is typically implemented using a stack or recursion. Compared with BFS, which uses a queue and explores level by level, DFS uses stack behavior and explores in depth. Its time complexity is O(V + E), and it is commonly used for traversal, connected components, cycle detection, and many grid-based interview problems.

Pattern to remember

DFS = "Go deep first" General graph: visit node mark visited for each neighbor: if not visited: dfs(neighbor) Grid: if out of bounds or invalid: return mark visited dfs in 4 directions

Final takeaway

The cleanest theoretical explanation is: DFS and BFS are similar traversal frameworks, but BFS is controlled by a queue and explores by levels, while DFS is controlled by a stack and explores by depth.

That is a strong interview answer because it is simple, accurate, and shows that you understand both the conceptual similarity and the practical difference.

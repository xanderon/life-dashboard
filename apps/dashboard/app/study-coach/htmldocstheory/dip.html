Technical Interview Study Page

Dependency Inversion Principle (DIP)

A core SOLID principle that says high-level business logic should depend on abstractions, not concrete implementations. This makes code easier to change, test, and extend.

OOP SOLID Design Principles Architecture Interview Theory

Definition

The Dependency Inversion Principle says that high-level modules should not depend on low-level modules. Instead, both should depend on abstractions.

In one line

Depend on interfaces / contracts, not directly on concrete classes.

Intuition

  • Business logic changes for business reasons.
  • Infrastructure code changes for technical reasons.
  • These two should not be tightly glued together.
  • Without DIP, changing a database, logger, or payment provider can force changes in core logic.
Without DIP

Your service becomes tightly coupled to implementation details like MySQLDatabase, StripeAPI, or ConsoleLogger.

Mental Model

Think about a wall socket. Your laptop does not connect directly to the electric grid internals. It connects through a standard interface.

Remember

Socket = abstraction
Device = high-level module
Power source details = low-level implementation

How It Works

1
Define an abstraction
Create an interface or contract that describes what the dependency should do.
2
Implement that abstraction
Concrete classes like MySQLDatabase or MongoDatabase implement the same contract.
3
Inject the dependency
The high-level module receives the dependency from outside instead of creating it with new inside itself.
4
Use the abstraction
The business logic works against the contract, so implementations can be replaced without changing the core logic.

Visual Diagram

Without DIP
───────────
OrderService ─────▶ MySQLDatabase

Problem:
If MySQL changes to MongoDB, OrderService may also need changes.


With DIP
────────
                  DatabaseInterface
                   ▲            ▲
                   │            │
            MySQLDatabase   MongoDatabase
                   ▲
                   │
              OrderService

Key idea:
- Control flow still goes from OrderService to the database.
- But the dependency is now on the abstraction, not the concrete class.

Example

class MySQLDatabase {
  save(order) {
    console.log("Saved to MySQL");
  }
}

class OrderServiceBad {
  constructor() {
    this.db = new MySQLDatabase();
  }

  createOrder(order) {
    this.db.save(order);
  }
}
Why this is bad
  • OrderServiceBad is tightly coupled to MySQLDatabase.
  • Harder to switch to another storage implementation.
  • Harder to unit test because the dependency is created internally.
class MySQLDatabase {
  save(order) {
    console.log("Saved to MySQL");
  }
}

class MongoDatabase {
  save(order) {
    console.log("Saved to MongoDB");
  }
}

class OrderService {
  constructor(database) {
    this.db = database;
  }

  createOrder(order) {
    this.db.save(order);
  }
}

const db = new MySQLDatabase();
const service = new OrderService(db);
service.createOrder({ id: 1 });
Why this is better
  • OrderService no longer decides which database to create.
  • You can inject MySQLDatabase, MongoDatabase, or a fake test double.
  • The high-level module depends on behavior, not on details.

Step-by-Step Explanation

  1. The service needs to save an order.
    That is business logic.
  2. Saving is a technical detail.
    It could be MySQL, MongoDB, Redis, or even an external API.
  3. If the service directly creates the database object, it becomes tightly coupled to one implementation.
  4. If the dependency is injected from outside, the service only cares that the object has the required behavior.
  5. This separation is what DIP protects.
    Business logic stays stable while details can change more freely.

Comparison

DIP vs Dependency Injection

  • DIP = design principle
  • Dependency Injection = implementation technique
  • DIP says what kind of design you want
  • DI is one common way to achieve it

DIP vs Direct Instantiation

  • Direct instantiation: new MySQLDatabase() inside the class
  • DIP style: receive dependency from outside
  • Direct instantiation is simpler at first
  • DIP is more flexible and testable long-term

Common Mistakes / Confusions

1. Confusing DIP with DI

They are related, but they are not the same thing. DIP is the principle. DI is a way to implement it.

2. Creating the dependency inside the class

If your class does this.db = new MySQLDatabase(), you usually lost the main benefit of DIP.

3. Making interfaces for everything

DIP is useful when you want flexibility, replacement, or easier testing. Not every tiny class needs an abstraction.

4. Thinking DIP changes runtime flow

The service still calls the dependency at runtime. What changes is the design dependency direction.

Real-World Use Cases

  • Repository pattern in backend services
  • Swapping database providers
  • Payment gateway abstraction
  • Logging through a logger interface
  • Email / SMS / push notification providers
  • Mocking dependencies in unit tests
Backend example

UserService depends on UserRepository, not directly on MongoDB code.

Interview Insights

  • Be able to define DIP clearly in one sentence.
  • Know the difference between abstractions and implementations.
  • Explain why DIP improves testability.
  • Explain why DIP reduces coupling.
  • Know that DI frameworks often help implement DIP.
  • Know the trade-off: more flexibility, but sometimes more boilerplate.

Interview Explanation Version

The Dependency Inversion Principle says that high-level business logic should not depend directly on low-level implementation details. Both should depend on abstractions, such as interfaces. This reduces coupling and makes the code easier to test, extend, and change. For example, a service should depend on a repository interface, not directly on MongoDB or MySQL code.

Pattern to Remember

Bad
───
High-level module ─────▶ Concrete implementation

Good
────
High-level module ─────▶ Abstraction ◀───── Concrete implementation

Memorize:
"Depend on abstractions, not details."

Summary

  • DIP is about depending on abstractions instead of concrete classes.
  • It reduces coupling between business logic and technical details.
  • It makes code easier to test because you can inject mocks or fakes.
  • It is closely related to Dependency Injection, but it is not the same thing.
  • It is most useful where implementations may change or where testability matters.
  • In interviews, emphasize flexibility, testability, and separation of concerns.

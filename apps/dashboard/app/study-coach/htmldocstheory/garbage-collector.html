JavaScript Garbage Collection Heap Call Stack Closures Memory Leaks Interview Prep

Definition

Core idea

The Garbage Collector reclaims memory from the heap when objects are no longer reachable. An object is reachable if there is still a valid chain of references from a GC root to that object.

GC does not ask: “Does this object exist somewhere in memory?” It asks: “Can I still reach this object starting from the roots?”

Tags / Category

This topic is a theoretical concept with practical debugging implications. It is very common in backend interviews because it tests whether you really understand memory, references, closures, and leaks beyond surface-level definitions.

Problem Statement

What often confuses candidates

Many people say “GC deletes objects with no references,” but they stop too early. The more correct idea is: GC deletes objects that are not reachable from roots.

That is why global arrays, event listeners, timers, and closures can keep objects alive even after a function has already finished.

Intuition

Mental shortcut

Imagine the runtime shines a flashlight from a few starting points called roots. Every object the light can reach stays alive. Everything left in the dark is garbage.

ROOTS │ ├── global variables ├── variables currently on the call stack ├── active closures └── runtime-held references (timers, listeners, callbacks) │ ▼ reachable objects in heap │ ▼ more referenced objects Anything not reached by this traversal → garbage
Key distinction

Stack is about active execution.

Heap is where objects live.

GC mainly cleans the heap, but it uses the call stack and other roots as the starting points for deciding what is still alive.

Mental Model

What is a root?

A root is a starting reference that the runtime knows is still accessible. Common examples are global variables and local variables inside stack frames that are currently active.

What is reachable?

An object is reachable if the runtime can follow references from a root all the way to that object.

What happens when a function returns?

Its stack frame is removed. If that frame was the only thing referencing an object, the object becomes eligible for GC.

Why do closures matter?

A closure can keep variables alive even after the outer function has finished, because the returned function still references them.

Step-by-step: How Mark-and-Sweep Works

Start from GC roots. These are the known entry points the runtime considers alive.
Traverse references. Follow every reference from those roots into heap objects.
Mark reachable objects. Anything visited during traversal is considered alive.
Sweep unreachable objects. Anything not marked is considered garbage and can be reclaimed.
Interview-safe wording

Most modern JavaScript engines use a mark-and-sweep style approach, often combined with generational garbage collection, where short-lived objects are collected more frequently.

Examples

1) Local variable becomes unreachable after function return

function test() {
  const user = { name: "Alex" };
}

test();
During execution: Call Stack ----------- test frame user → 0xA1 Heap ---- 0xA1 → { name: "Alex" } After function returns: Call Stack ----------- (empty / back to caller) Heap ---- 0xA1 → { name: "Alex" } No root can reach 0xA1 anymore → eligible for GC
What matters here

The object still physically exists in heap for a while, but that does not matter. Once it becomes unreachable, GC may reclaim it later.

2) Returned object survives because root still references it

function test() {
  const user = { name: "Alex" };
  return user;
}

const u = test();
ROOT │ ▼ u → 0xA1 Heap ---- 0xA1 → { name: "Alex" }

The object does not get collected because u is still a root-level reference to it.

3) Closure keeps data alive

function createUser() {
  const user = { name: "Alex" };

  return function () {
    console.log(user.name);
  };
}

const fn = createUser();
ROOT │ ▼ fn │ ▼ closure function │ ▼ user object
Common confusion

The outer function finished, but the closure still references user. So user is still reachable and cannot be garbage collected yet.

4) Global cache can create a memory leak

let cache = [];

function addUser() {
  const user = { name: "Alex" };
  cache.push(user);
}

addUser();
ROOT │ ▼ cache │ ▼ array │ ▼ user object

Even after addUser() returns, the object stays alive because the global array still references it. If this array keeps growing, memory usage keeps growing too.

5) Circular references alone are not a problem

let a = {};
let b = {};

a.ref = b;
b.ref = a;

a = null;
b = null;
Heap ---- 0xA1 → ref → 0xB1 0xB1 → ref → 0xA1 But no root points to either object anymore.
Important interview point

Modern mark-and-sweep collectors can still delete these objects. Circular references only used to be a big issue in simple reference-counting systems.

Line-by-line Explanation of the Most Important Example

let cache = [];

function addUser() {
  const user = { name: "Alex" };
  cache.push(user);
}

addUser();
let cache = []; creates a global array. Because it is global, it is reachable from a root.
const user = { name: "Alex" }; creates an object in heap and stores a local reference in the stack frame of addUser.
cache.push(user); stores the same object reference inside the global array.
The function returns, so the local variable user disappears from the stack.
But the global array still holds the reference, so the object remains reachable and cannot be collected.

Call Stack vs Heap in This Topic

Concept What it holds Why it matters for GC
Call Stack Active function frames, local variables, current execution context Variables in active frames act like roots for reachability
Heap Objects, arrays, functions, closures This is the memory area GC reclaims when objects become unreachable
Global Scope Long-lived references such as module-level arrays or caches Can accidentally keep many heap objects alive
Closures Functions plus references to outer lexical variables Can keep data alive even after the outer function returns

Common Mistakes / Confusions

High-frequency interview traps
  • Saying “an object is alive if it has any reference anywhere” instead of saying reachable from roots.
  • Confusing GC roots with young generation vs old generation.
  • Thinking circular references automatically mean a memory leak.
  • Thinking a closure lives forever. It lives only while something still references that function.
  • Thinking an object is destroyed immediately when a function returns. It becomes eligible for collection, but GC runs later.
  • Forgetting that event listeners, timers, and caches may be long-lived runtime references.

Generational GC (Relevant Bonus Point)

A strong interview answer can mention that modern runtimes often use generational GC. The key idea is:

Most objects die young.

So the engine often collects newer objects more frequently and checks older, long-lived objects less often. This is a performance optimization on top of the basic reachability idea.

Interview Explanation Version

20–30 second answer

Garbage Collection in JavaScript reclaims memory from the heap when objects are no longer reachable. The runtime starts from GC roots like global variables and current call stack variables, marks everything reachable from them, and removes the rest. Closures, global caches, event listeners, and timers can accidentally keep objects alive and cause memory leaks.

45 second stronger answer

JavaScript garbage collection is based on reachability, not just raw existence in memory. The runtime starts from GC roots such as global variables, active stack frames, closures, and runtime-held references. It traverses all references from those roots, marks reachable objects, and then sweeps away unreachable ones. This is why local objects inside finished functions usually become collectible, while objects stored in global arrays or captured by closures stay alive. Modern engines also use generational GC because most objects have a short lifetime.

Pattern to Remember

If there is a path from ROOTS to the object: keep it If there is no path from ROOTS to the object: collect it

Real-world Use Cases / Debugging Relevance

Global caches

Useful for performance, but dangerous if they grow without limits or eviction rules.

Event listeners

If listeners are never removed, they can keep closures and large objects alive much longer than expected.

Intervals and timers

A setInterval callback can keep references alive because the runtime still holds the callback.

Long-lived closures

Handy for encapsulation, but easy to misuse if they retain large data structures.

Final Explanation

The cleanest way to understand garbage collection is this: GC is a graph traversal problem. Roots are the entry points, references are the edges, and heap objects are the nodes. If the runtime can still walk from a root to a node, the node stays alive. If it cannot, the node becomes garbage.

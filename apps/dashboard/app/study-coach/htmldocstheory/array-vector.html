Array / Vector

A clean interview-focused study page built from the discussion in this chat. The topic here is a theoretical concept with practical implications: what an array really is, why it is fast, where it becomes slow, and how it compares to alternatives like linked lists and dynamic arrays.

Definition

Simple definition

An array is a data structure that stores elements in contiguous memory and lets you access each element by its index.

In interview language: the big idea is that arrays are fast for read by index, but expensive when you need to insert or delete in the middle.

Intuition — Why does this exist?

If you have many values of the same kind, you need a structure that lets you store them together and access them predictably. Without arrays, you would end up with many separate variables, which becomes unmanageable almost immediately.

Without an array

You get things like score1, score2, score3, which do not scale and are hard to loop through.

With an array

You get scores[0], scores[1], scores[2], so the data becomes organized, iterable, and easy to process.

The key benefit is this: if you know the index, the machine can usually go directly to the right memory location instead of searching element by element.

Mental model

Think of a row of numbered lockers

Each locker has a fixed position: locker 0, locker 1, locker 2, and so on. If someone asks for locker 3, you go directly there.

That is the essence of an array: position-based access.

Index: 0 1 2 3 4 ┌─────┬─────┬─────┬─────┬─────┐ Value: │ 10 │ 25 │ 33 │ 17 │ 8 │ └─────┴─────┴─────┴─────┴─────┘

How it works conceptually

The main reason arrays are powerful is that their elements are stored in consecutive memory addresses.

Suppose: base address = 1000 element size = 4 bytes Then: array[0] → address 1000 array[1] → address 1004 array[2] → address 1008 array[3] → address 1012
Core formula

The runtime can compute the address directly:

address = base_address + index × element_size

That is why reading array[i] is typically O(1).

Visualization in memory

Memory addresses: 1000 1004 1008 1012 1016 ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ │10 │ │20 │ │30 │ │40 │ │50 │ └───┘ └───┘ └───┘ └───┘ └───┘ 0 1 2 3 4 If we want array[3]: address = 1000 + 3 × 4 = 1012

Example step by step

const numbers = [10, 20, 30, 40];

console.log(numbers[2]); // 30
The array is created. The runtime stores the values in order, one after another in memory. The important idea is not the exact byte addresses in JavaScript, but the mental model: arrays are treated like indexed sequences with fast positional access.
You ask for numbers[2]. That means “give me the element at index 2,” not “search for value 2.”
The runtime computes where that element should be. Conceptually: base + index × element_size.
Why? Because the elements are laid out in a predictable order.
The value is returned immediately. That is why access by index is considered O(1).

Complexity

Operation Complexity Why
Access by index O(1) Direct address calculation
Update by index O(1) You already know where the slot is
Linear search O(n) You may need to inspect many elements
Insert in middle O(n) Elements after that position must be shifted
Delete in middle O(n) Remaining elements must be shifted left
Append at end O(1) amortized Usually constant, but resizing occasionally makes it expensive
Important interview nuance

For many modern languages, what you use in practice is often a dynamic array / vector, not a raw fixed-size array. That is why append is usually described as O(1) amortized.

Array vs Vector / Dynamic Array

This distinction matters because many candidates blur them together.

Concept Array Vector / Dynamic Array
Size Usually fixed Can grow automatically
Memory layout Contiguous Also contiguous
Append Only if there is space Usually O(1) amortized
Resize Not automatic Reallocates to a bigger block when needed
Examples C-style arrays C++ vector, Java ArrayList, JS arrays
Interview-safe wording

In practice, JavaScript arrays behave more like dynamic arrays than raw low-level arrays. But the main array intuition still applies: indexed access is fast; middle insertions are expensive.

Real-world use cases

Backend

Lists of users, products, jobs, devices, records returned from a repository or database query.

Node.js

Batch processing, loops over tasks, request results, temporary buffers of work items, collections of messages.

Web apps

Rendering lists of items, mapping UI components, sorting or filtering search results.

Algorithms

Two Sum, sliding window problems, sorting, binary search on sorted arrays, prefix sums.

Examples of real bugs and bad patterns

1) Unbounded in-memory array

const cache = [];

function add(item) {
  cache.push(item);
}
Why the problem appears

The array keeps growing and nothing removes old items. Memory usage rises continuously.

What remains in memory? Every object you pushed that still has a reference through cache.

2) Logging requests into an array forever

const logs = [];

app.use((req, res, next) => {
  logs.push(req);
  next();
});
What goes wrong

You retain request objects in memory. Over time that can become a memory leak or at least serious memory pressure.

3) Producer is faster than consumer

const messages = [];

function onMessage(msg) {
  messages.push(msg);
}
Why it is dangerous

If new messages arrive faster than they are processed, the array becomes a growing backlog. This is really a backpressure problem, but the symptom is often “the array exploded.”

How this connects to other CS concepts

  • Stack — often implemented on top of a dynamic array.
  • Queue — can be implemented with arrays, though naive front deletion may be expensive.
  • Matrix — conceptually an array of arrays.
  • Hash table — internally uses array-like buckets.
  • Binary search — becomes powerful because arrays support indexed access.
  • CPU cache locality — arrays are often faster in practice because their data is close together in memory.

Interviewers often want to see whether you understand not just how to code with arrays, but why certain operations are cheap and others are not.

Common interview questions

Why is array access O(1)?

Because the address can be computed directly from the base address and the index.

Why is insertion in the middle O(n)?

Because all later elements may need to be shifted to make room.

What is a dynamic array?

A resizable array that grows by allocating a larger contiguous block and copying elements over when capacity is exceeded.

Why is append often described as amortized O(1)?

Because most appends are cheap, but occasionally a resize makes one append expensive. Spread across many operations, the average cost is constant.

Trick questions / common traps

“Search in an array is O(1)”

False. Access by index is O(1). Searching by value is usually O(n).

“Insertion is O(1)”

Only at the end in a dynamic array, and even then it is usually described as O(1) amortized.

“Arrays are always fixed-size”

Low-level arrays often are, but many languages mostly expose dynamic arrays in daily use.

“Index means value”

No. The index is the position, not the content.

Common mistakes and confusions

  • Mixing up index lookup with value search.
  • Forgetting the difference between length and capacity.
  • Assuming a JavaScript array behaves exactly like a low-level C array.
  • Ignoring that repeated insertions near the front or middle can make an array-based solution slow.
  • Using arrays as unbounded storage and accidentally creating memory problems.

Feynman technique — explain it like to a 10-year-old

Simple explanation

Imagine a shelf with boxes numbered 0, 1, 2, 3, 4. If I ask for box number 3, you can go straight to it.

That is what an array does: it stores things in order, and because every spot has a number, you can reach one very quickly.

But if you want to put a new box in the middle, you have to move the others to make space. That is why some operations are fast and others are slow.

Interview explanation version

An array stores elements in contiguous memory, which makes access by index very fast — typically O(1) — because the address can be computed directly.

The trade-off is that insertion or deletion in the middle is expensive, usually O(n), because elements have to be shifted.

In modern languages, we often work with dynamic arrays or vectors, which keep the same indexed-access advantage but can resize automatically, giving append an amortized O(1) cost.

Pattern to remember

The core pattern

Array = fast by position, expensive to reshape.

Or even shorter:

Read fast. Insert in middle slow.

Interface Segregation Principle (ISP)

The I in SOLID. The core idea: a class should not be forced to depend on methods it does not use. Instead of one large, general-purpose interface, prefer smaller and focused interfaces that match real behavior.

SOLID OOP Design Principles Interfaces Abstract Classes Interview Theory

Definition

Formal interview definition

Interface Segregation Principle says that clients should not be forced to depend on methods they do not use. In practice, this means we should prefer small, specific interfaces over large, generic ones.

A “client” can be a class, service, module, or implementation that consumes a contract. That contract can be an interface, but the same idea also applies to abstract classes and public APIs in general.

Intuition

Imagine you give someone a form with 10 responsibilities, but they only actually need 2. The other 8 are noise, confusion, and accidental coupling.

ISP says: don’t design contracts around “everything this domain could ever do.” Design them around what a specific client actually needs.

Mental shortcut

If an implementation has to write methods like throw new Error("Not implemented"), empty bodies, fake returns, or comments like // not needed here, that is usually a strong signal that the interface is too big.

Mental Model

Bad design

One large contract tries to describe too many behaviors at once. Classes are forced to implement features they do not support.

Good design

Multiple focused contracts each represent one coherent capability. Classes implement only what they truly provide.

Simple memory phrase

Many small focused interfaces > one fat interface.

Classic Example: Printer, Scanner, Fax

This is the standard example because it shows the problem immediately. Some devices can print, scan, and fax. Others can only print. A single “all-in-one” contract becomes a bad fit for simpler devices. 

class Document {}

class Machine {
  print(doc) {}
  scan(doc) {}
  fax(doc) {}
}

class MultiFunctionPrinter extends Machine {
  print(doc) {
    console.log("Printing document");
  }

  scan(doc) {
    console.log("Scanning document");
  }

  fax(doc) {
    console.log("Faxing document");
  }
}

class BasicPrinter extends Machine {
  print(doc) {
    console.log("Printing document");
  }

  scan(doc) {
    throw new Error("BasicPrinter cannot scan");
  }

  fax(doc) {
    throw new Error("BasicPrinter cannot fax");
  }
}
Why this violates ISP

BasicPrinter is forced to depend on scan() and fax() even though it does not use them and does not support them. The contract is too broad.

Better version

class Printer {
  print(doc) {}
}

class Scanner {
  scan(doc) {}
}

class Fax {
  fax(doc) {}
}

class BasicPrinter extends Printer {
  print(doc) {
    console.log("Printing document");
  }
}

class MultiFunctionPrinter extends Printer {
  print(doc) {
    console.log("Printing document");
  }

  scan(doc) {
    console.log("Scanning document");
  }

  fax(doc) {
    console.log("Faxing document");
  }
}
What improved

Now each capability is separated. A simple printer only depends on printing. A more advanced machine can support more behaviors without forcing all devices to pretend they can do everything.

Example from This Chat: Notification System

Another example we discussed was a notification system with multiple channels: email, SMS, and Slack. 

class NotificationService {
  sendEmail(message) {}
  sendSMS(message) {}
  sendSlack(message) {}
}

class EmailNotifier extends NotificationService {
  sendEmail(message) {
    console.log("Sending email:", message);
  }

  sendSMS(message) {
    throw new Error("Not supported");
  }

  sendSlack(message) {
    throw new Error("Not supported");
  }
}

The problem is the same. EmailNotifier only knows email, but the contract forces it to pretend it also knows SMS and Slack.

Better split

class EmailSender {
  sendEmail(message) {}
}

class SmsSender {
  sendSMS(message) {}
}

class SlackSender {
  sendSlack(message) {}
}

class EmailNotifier extends EmailSender {
  sendEmail(message) {
    console.log("Sending email:", message);
  }
}

class SmsNotifier extends SmsSender {
  sendSMS(message) {
    console.log("Sending SMS:", message);
  }
}
Important nuance

The point is not “split everything into tiny pieces no matter what.” The point is to split when one interface combines unrelated responsibilities and starts forcing implementations to carry methods they do not need.

Step-by-Step Explanation

Step 1 — Find the contract

Look for an interface, abstract class, or public API that defines several methods.

Step 2 — Check the implementations

Ask: do all implementations genuinely need all of these methods?

Step 3 — Look for pain signals

Are there empty methods, fake implementations, errors like Not implemented, or conditional logic just to avoid unsupported behavior?

Step 4 — Split by capability

Extract small interfaces around real responsibilities such as printing, scanning, faxing, sending email, sending SMS, and so on.

Step 5 — Let implementations depend only on what they use

Each class now implements only the contract that matches its actual behavior.

How It Also Applies to Abstract Classes

In discussion, one subtle point was whether ISP applies only to interfaces. The answer is no. It applies to contracts in general.

Good interview phrasing

ISP is usually explained using interfaces, but the same principle applies to abstract classes too, because they can also force subclasses to depend on behavior they do not need. 

class AbstractNotificationService {
  sendEmail(message) {}
  sendSMS(message) {}
  sendSlack(message) {}
}

class EmailOnlyService extends AbstractNotificationService {
  sendEmail(message) {
    console.log("Email sent:", message);
  }

  sendSMS(message) {
    throw new Error("Not supported");
  }

  sendSlack(message) {
    throw new Error("Not supported");
  }
}

Even though this is an abstract base-style design instead of an interface-style design, the underlying problem is identical: the contract is too large for some clients.

Common Mistakes / Confusions

Confusion #1 — “It means make everything tiny”

Not exactly. ISP does not mean endless fragmentation. It means interfaces should be cohesive and should not force unrelated behavior.

Confusion #2 — “Only interfaces are affected”

No. The principle applies to abstract classes and any public contract.

Confusion #3 — “A large interface is always bad”

Not always. A large interface is fine if every implementation truly needs and supports all of it. The issue is forced dependency on unused behavior.

Confusion #4 — “This is the same as SRP”

They are related, but not identical. SRP is about a class/module having one reason to change. ISP is about clients not depending on methods they do not use.

Red Flags That Usually Mean ISP Is Violated

  • Methods that just throw NotImplemented errors.
  • Empty method bodies added only to satisfy a contract.
  • Comments like // not used here in implementations.
  • One “god interface” with many unrelated methods.
  • Implementations supporting only a small subset of the contract.

Real-World Use Cases

  • Notification systems: email, SMS, push, Slack, WhatsApp should not all live in one forced contract.
  • File storage: not every storage provider supports read, write, delete, versioning, and signed URLs equally.
  • Payments: some providers support refunds, some support subscriptions, some only one-time payments.
  • Microservices: one consumer may only need getById(), not an entire repository contract with 12 methods.
  • Device capabilities: some devices can print only, others can print and scan, others can do more.

Final Takeaway

Final explanation

Interface Segregation Principle is about keeping contracts aligned with real behavior. If a class is forced to implement methods it does not support, the contract is too broad. The fix is to split that contract into smaller, meaningful interfaces so each client depends only on what it actually needs.

In interview terms, the cleanest answer is:

Best one-liner

ISP means small, focused contracts that do not force unused methods onto implementations.

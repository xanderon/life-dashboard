HashMap / Dictionary
and Why Map.get([1,2,3]) Returns undefined

A clean interview-focused study page based on this chat: what a HashMap is, why it exists, how it works conceptually, and the very important JavaScript trap that Map compares arrays and objects by reference, not by structural value.

Definition

Simple definition

A HashMap (or Dictionary) is a data structure that stores key → value pairs and gives fast average-time access to values using their keys.

JavaScript angle

In JavaScript, Map is a built-in key-value structure. It can use primitives, objects, arrays, and functions as keys. But for objects and arrays, keys are compared by reference identity.

Intuition — Why does this structure exist?

Without a HashMap, if you want to find something by key, you often scan a list until you hit the matching element. That is usually O(n).

A HashMap exists to avoid that repeated scanning. Instead of searching linearly, it tries to jump directly to the place where the item should live.

Without HashMap

Search through a list one by one:

["Ana", "Maria", "Ion", "George"] ↓ check Ana check Maria check Ion ✓

Typical idea: linear search → O(n).

With HashMap

Use the key to compute where the value should be:

key ↓ hash(key) ↓ index ↓ bucket[index]

Typical idea: direct lookup → average O(1).

Mental model

Think of a HashMap like a cabinet full of numbered drawers.

If you want an item, you do not open every drawer. You run the key through a rule that tells you which drawer to open.

"user123" ↓ hash("user123") = some big number ↓ big number % number_of_drawers ↓ drawer 6
The key idea to remember: a HashMap is trying to replace searching with computing.

How it works conceptually

A HashMap usually has these pieces:

  • An internal array of buckets.
  • A hash function that transforms a key into a number.
  • An index calculation, often something like hash(key) % capacity.
hash("apple") = 981723 capacity = 10 index = 981723 % 10 = 3 → store "apple" in bucket[3]

But what about collisions?

Different keys can end up at the same index. That is called a collision.

hash("cat") % 10 = 3 hash("dog") % 10 = 3 Both want bucket[3]

Real implementations solve this with techniques like chaining or open addressing.

Visualization / ASCII diagram

Bucket array 0 → [ ] 1 → [ ] 2 → [ ("user1", "Alex") ] 3 → [ ] 4 → [ ("user2", "Maria") ] 5 → [ ] 6 → [ ] 7 → [ ] 8 → [ ] 9 → [ ]

Lookup is conceptually:

"user2" ↓ hash("user2") ↓ index = hash % size ↓ go directly to bucket[4] ↓ find value "Maria"

Simple JavaScript example

const map = new Map();

map.set("user1", "Alex");
map.set("user2", "Maria");
map.set("user3", "John");

console.log(map.get("user2")); // "Maria"

Step by step

Step 1

map.set("user1", "Alex") stores a relationship between the key and the value.

Conceptually, the engine computes where that key belongs and stores it there.

Why?

So later, when you ask for "user1", the engine can jump close to the answer instead of scanning everything.

Step 2

map.get("user2") runs the same process on the key "user2".

Same key → same computed location.

Why?

That is why key-based lookup is fast: the location is derived from the key itself.

The key trap from this chat: arrays and objects as keys

This is where many candidates get confused. 

const map = new Map();
const arr = [1, 2, 3];

map.set(arr, "valoare");

console.log(map.get([1, 2, 3])); // undefined
console.log(map.get(arr));       // "valoare"
Important

In JavaScript Map, object keys and array keys are compared by reference, not by structural content.

What does “by reference” mean?

When you create an array or object, the variable does not hold the full structure itself in the same way a primitive does. It holds a reference to that object in memory.

const arr = [1, 2, 3] arr ─────► [1, 2, 3]

Why does map.get([1, 2, 3]) fail?

Because [1, 2, 3] in that call creates a new array instance. Even though it looks identical, it is a different object in memory.

Original: arr ─────► [1, 2, 3] (ref_1) New lookup array: ─────► [1, 2, 3] (ref_2) Map stores: ref_1 → "valoare" Lookup asks for: ref_2 ref_1 !== ref_2 → undefined

Why does map.get(arr) work?

Because arr is the exact same reference that was used during set.

Reference vs value

Primitives are compared by value
console.log(5 === 5);           // true
console.log("abc" === "abc");   // true
Objects and arrays are compared by reference
console.log([1, 2, 3] === [1, 2, 3]); // false

const a = [1, 2, 3];
const b = a;

console.log(a === b); // true

In other words:

  • [1,2,3] and [1,2,3] look the same, but they are two different objects.
  • a and b can be equal only if they point to the same object.

Step-by-step memory picture for the Map key trap

const map = new Map(); const arr = [1, 2, 3]; map.set(arr, "valoare"); Heap: ref_1 → [1, 2, 3] Map: ref_1 → "valoare" Now: map.get([1, 2, 3]) This creates: ref_2 → [1, 2, 3] Map has ref_1, not ref_2 → result: undefined
Pattern to remember

For object-like keys in JavaScript Map, the question is not “Does it look the same?” but “Is it the exact same object?”

Complexity

Operation Average Time Worst Case Intuition
Insert O(1) O(n) Usually go straight to the bucket; collisions can degrade performance.
Lookup O(1) O(n) Fast if the key distribution is good.
Delete O(1) O(n) Usually remove directly by computed location.
Space O(n) O(n) You need extra memory for the internal storage structure.

Important interview nuance: HashMap operations are usually described as average-case O(1), not guaranteed O(1) in every possible situation.

Common mistakes / confusions

Mistake 1

Thinking HashMap means “magic constant time no matter what.” It is average-case fast, but collisions can make it worse.

Mistake 2

Assuming two arrays with the same elements are the same key in Map. They are not, unless they are the exact same reference.

Mistake 3

Forgetting that object/array equality in JavaScript is identity-based, not deep-value-based.

Mistake 4

Using a cache or Map with object keys without realizing that recreating the object later will not hit the same entry.

  freq.set(ch, (freq.get(ch) || 0) + 1);

console.log(freq);

A Map with object keys is useful when you want to cache results for the same exact object instance.

When object-keyed Map is useful vs when it is a trap

Good use
const cache = new Map();

function compute(user) {
  if (cache.has(user)) return cache.get(user);

  const result = heavyOperation(user);
  cache.set(user, result);
  return result;
}

This works if the same exact user object instance comes back again.

Trap
const cache = new Map();

cache.set({ id: 1 }, "value");

console.log(cache.get({ id: 1 })); // undefined

This fails because the lookup object is a new reference.

If you need “same value” instead of “same reference”

Sometimes you do not want object identity. You want structural equality. In that case, a plain Map with object keys is not enough by itself.

Option 1: convert to a stable string key

const map = new Map();

const key = JSON.stringify([1, 2, 3]);
map.set(key, "valoare");

console.log(map.get(JSON.stringify([1, 2, 3]))); // "valoare"
Caution

This can be useful, but it has trade-offs. Stringifying can be slower, property order can matter for objects, and not every structure serializes cleanly.

Option 2: design a stable key yourself

const map = new Map();

function makeKey(arr) {
  return arr.join(",");
}

map.set(makeKey([1, 2, 3]), "valoare");

console.log(map.get(makeKey([1, 2, 3]))); // "valoare"

Interview explanation version

30-second answer

A HashMap stores key-value pairs and uses a hash function to map each key to a location in an internal array, which gives average O(1) insert and lookup. In JavaScript, Map is the built-in structure for this idea. One important detail is that object and array keys are compared by reference, not by structural value, so map.get([1,2,3]) will not match a value stored with another array literal that only looks the same.

Slightly deeper answer

Internally, a hash-based structure computes a numeric representation of a key, then maps it into a bucket index. That is why it avoids linear search. The average complexity is constant time, but collisions can degrade it. In JavaScript specifically, primitives behave more intuitively as keys, while arrays and objects behave by identity. So the key question becomes: is this the exact same object, or just a new object with the same content?

Pattern to remember

Memory hook

HashMap: “Do not search, compute where to look.”

JavaScript Map object keys: “Same shape is not enough. Same reference is required.”

HashMap idea: key → hash → bucket → value JavaScript Map object key idea: object key works only if it is the same exact object instance

Final takeaway

The big idea from this topic is not just that HashMaps are fast. It is why they are fast and what trade-off makes that possible.

They are fast because they avoid searching and instead compute where data should be. In JavaScript, Map gives you this key-value model, but when the key is an array or object, equality is based on identity, not content.

If an interviewer asks why map.get([1,2,3]) is undefined, the best answer is: because that array literal creates a new reference, and Map compares object keys by reference, not by deep value.

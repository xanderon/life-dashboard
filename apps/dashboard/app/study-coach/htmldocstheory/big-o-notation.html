Big O Notation

Interview-focused study page for understanding time complexity, space complexity, the common Big-O order, real intuition for log n and n log n, and the classic mistakes people make when explaining complexity out loud.

Algorithms Big O Time Complexity Space Complexity Interview Prep Theory

Definition

What Big O means

Big O notation describes how the cost of an algorithm grows as the input size n grows. In interviews, this usually means time complexity, but it can also mean space complexity.

Time = how long it runs Space = how much extra memory it uses
Big O is not about the exact runtime in milliseconds. It is about how the algorithm scales when the input gets large.

Correct Order of the Common Complexities

Order Complexity Meaning Typical Example
1 O(1) Constant time Array index access, stack push/pop, queue enqueue/dequeue, hash map get/set average case
2 O(log n) Input keeps getting cut in half Binary search
3 O(n) Linear scan Single loop through all elements
4 O(n log n) Divide + process everything Merge sort, quicksort average case
5 O(n²) Nested iteration Loop inside loop, bubble sort
6 O(2^n) Exponential growth Naive Fibonacci, generate all subsets
7 O(n!) Factorial explosion Generate all permutations, brute-force TSP
Important ordering reminder

O(n log n) is better than O(n²). A very common mistake is to mix these up.

Mental Model

How to think about log n

You do not need advanced logarithm math for interviews. Just think:

How many times can I divide by 2 until I reach 1?

Example for n = 8:

8 → 4 → 2 → 1

That is 3 steps, so log₂(8) = 3.

How to think about the “double the input” trick

This is just an intuition trick: If the input becomes twice as big, how much worse does the algorithm become?

  • O(1) → almost no change
  • O(log n) → only a tiny increase
  • O(n) → about 2x
  • O(n²) → about 4x

Step-by-Step Explanation of the Core Cases

O(1) — Constant time

The operation does not grow with input size. It stays effectively the same size of work.

Good examples: arr[i], stack push(), stack pop(), queue enqueue(), queue dequeue(), hash map lookup average case.

O(log n) — Keep cutting in half

If each step removes half of the remaining work, the number of steps grows logarithmically.

Classic example: binary search on a sorted array.

O(n) — Visit everything once

If you scan every item once, runtime grows linearly with input size.

Typical example: a single for loop over all elements.

O(n log n) — Divide, then process all

This is the most important interview pattern after O(n). Merge sort is the classic example.

You have:

log n levels n work per level

So total work becomes:

O(n log n)

O(n²) — Nested work

If for each element you iterate across all elements again, that is usually quadratic.

Typical example: a loop inside another loop over the same input.

O(2^n) — Exponential growth

This happens when each choice branches into two more choices. A much more realistic interview example than naive Fibonacci is: generate all subsets.

For each element, you decide:

include it exclude it

O(n!) — Factorial explosion

This appears when you generate every possible ordering of items.

The standard example is permutations.

Examples

O(1) examples

const value = arr[5];          // O(1)

stack.push(10);                // O(1)
stack.pop();                   // O(1)

queue.enqueue(10);             // O(1)
queue.dequeue();               // O(1)

map.get("userId");             // O(1) average
map.set("userId", user);       // O(1) average

O(log n) example — Binary Search

function binarySearch(arr, target) {
  let left = 0;
  let right = arr.length - 1;

  while (left <= right) {
    const mid = Math.floor((left + right) / 2);

    if (arr[mid] === target) return mid;
    if (arr[mid] < target) left = mid + 1;
    else right = mid - 1;
  }

  return -1;
}

O(n) example — Single loop

function sumArray(arr) {
  let total = 0;

  for (let i = 0; i < arr.length; i++) {
    total += arr[i];
  }

  return total;
}

O(n log n) example idea — Merge Sort pattern

// Conceptual view:
// 1. Split array in half
// 2. Split each half again
// 3. Merge them back while scanning all elements

// log n = number of split levels
// n = work done per level
// total = O(n log n)

O(n²) example — Nested loops

function printPairs(arr) {
  for (let i = 0; i < arr.length; i++) {
    for (let j = 0; j < arr.length; j++) {
      console.log(arr[i], arr[j]);
    }
  }
}

O(2^n) example — All subsets

function subsets(nums, index = 0, current = [], result = []) {
  if (index === nums.length) {
    result.push([...current]);
    return result;
  }

  // Exclude current element
  subsets(nums, index + 1, current, result);

  // Include current element
  current.push(nums[index]);
  subsets(nums, index + 1, current, result);
  current.pop();

  return result;
}

O(n!) example — Permutations

function permutations(nums, start = 0, result = []) {
  if (start === nums.length) {
    result.push([...nums]);
    return result;
  }

  for (let i = start; i < nums.length; i++) {
    [nums[start], nums[i]] = [nums[i], nums[start]];
    permutations(nums, start + 1, result);
    [nums[start], nums[i]] = [nums[i], nums[start]];
  }

  return result;
}

Time Complexity vs Space Complexity

Time complexity

Measures how runtime grows as the input grows.

Space complexity

Measures how much extra memory an algorithm uses as the input grows.

Important interview nuance

Space complexity usually means auxiliary space, not the memory of the input itself.

sumArray(arr)
Time: O(n)
Space: O(1)

It scans the array once and uses only a few variables.

copyArray(arr)
Time: O(n)
Space: O(n)

It creates a new array of size n.

mergeSort(arr)
Time: O(n log n)
Space: O(n)

It needs extra memory for merging.

function sumArray(arr) {
  let total = 0;

  for (let i = 0; i < arr.length; i++) {
    total += arr[i];
  }

  return total;
}
// Time: O(n)
// Space: O(1)
function copyArray(arr) {
  const result = [];

  for (let i = 0; i < arr.length; i++) {
    result.push(arr[i]);
  }

  return result;
}
// Time: O(n)
// Space: O(n)

Real Interview Clarifications

Why is array access O(1)?

Because arrays allow direct access by index. The runtime does not depend on how many elements are in the array.

Why is array insertion not always O(1)?

Appending at the end is usually O(1) amortized, but inserting at the beginning or middle is O(n) because elements must be shifted.

Why is hash map lookup only average O(1)?

In the worst case, many keys collide into the same bucket, and then lookup becomes linear inside that bucket. So the formal answer is:

Average: O(1) Worst case: O(n)

Why is merge sort O(n log n)?

Because it has log n levels of splitting, and each level processes all n elements.

Common Mistakes / Confusions

Mistake 1: Thinking O(n log n) is worse than O(n²)

It is not. O(n log n) scales much better than O(n²).

Mistake 2: Saying all array insertions are O(1)

Only appending to the end is typically O(1) amortized. Inserting in the middle or front is O(n).

Mistake 3: Forgetting worst case vs average case

Hash maps are the classic example: average O(1), worst case O(n).

Mistake 4: Mixing time and space

A function may be fast but use more memory, or use little memory but be slower. This is a classic trade-off.

Mistake 5: Thinking Big O means exact runtime

Big O ignores constants and focuses on growth. 2n, 3n, and 10n are all still O(n).

Interview Explanation Version

30-second answer

Big O notation describes how the cost of an algorithm grows as input size grows. Usually we talk about time complexity, but it can also describe space complexity. Common examples are O(1) for direct access, O(log n) for binary search, O(n) for a single scan, O(n log n) for merge sort, O(n²) for nested loops, O(2^n) for subset-style recursion, and O(n!) for permutations.

Why we care

We care about Big O because it helps us compare algorithms based on scalability, not just on small examples.

Time vs space

Time complexity tells us how runtime grows. Space complexity tells us how much additional memory is needed. Sometimes we trade memory for speed, like using a hash map for faster lookup.

Pattern to Remember

Fast recognition rules
  • Direct access → usually O(1)
  • Keep dividing by 2 → usually O(log n)
  • Visit everything once → usually O(n)
  • Divide + process all → usually O(n log n)
  • Loop inside loop → usually O(n²)
  • Two recursive choices per element → usually O(2^n)
  • All permutations → usually O(n!)

Real-World Use Cases

Why O(log n) matters

Fast searching in sorted data, database indexes, balanced trees, and any problem where each decision cuts the remaining search space.

Why O(n log n) matters

Efficient sorting is one of the most practical algorithmic tasks in software engineering.

Why O(2^n) appears in real interviews

Backtracking problems: subsets, combinations, decisions where every element creates a yes/no branch.

Why O(n!) matters

It is the warning sign that brute force becomes impossible very fast when trying every ordering.

Final Explanation

Big O notation is the language we use to describe scalability. The most important interview skill is not memorizing symbols, but recognizing the pattern: direct access, halving, scanning, nested loops, divide-and-process, exponential branching, or permutations.

If you can explain O(1), O(log n), O(n), O(n log n), O(n²), O(2^n), and O(n!) with one intuitive example each, you are already in a very strong place for technical interviews.

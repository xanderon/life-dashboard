LSP — Liskov Substitution Principle

Interview-focused study page built from the discussion in this chat. The core idea: a subtype must be usable anywhere the base type is expected, without breaking correctness, assumptions, or behavior.

OOP SOLID Design Principles Inheritance Polymorphism Interview Prep

Definition

Simple definition

Liskov Substitution Principle says that if Child extends Parent, then objects of Child should be usable everywhere Parent is expected, without breaking the program.

If I replace the base class with the derived class, the code should still behave correctly.

Intuition — Why does this principle exist?

Inheritance is easy to abuse. A child class may reuse code from a parent but still change the meaning of the contract. That is where bugs start.

Without LSP
  • You trust the parent type, but the child behaves differently.
  • Polymorphism becomes unsafe.
  • You start adding instanceof checks everywhere.
  • The code becomes fragile and surprising.
With LSP
  • Base abstractions become reliable.
  • Polymorphism stays useful.
  • Code depending on abstractions stays clean.
  • Inheritance models real behavior, not just code reuse.

Mental model

Think of a standard power socket

A socket defines a contract: plug in a compatible device and it should work safely. If one “compatible” device explodes the socket, then it was never truly compatible.

LSP is the same idea in software: the subtype must respect the contract of the base type.

Conceptual explanation

LSP is not just “the code compiles.” It is about preserving behavior and expectations.

1. Contract must stay valid

If the parent says a method does something, the child must not silently change its meaning.

2. Preconditions cannot become stricter

The child should not require more than the parent required in order to work.

3. Postconditions cannot become weaker

If the parent promises a certain result, the child must still honor that promise.

4. Invariants must remain true

The child must not break the internal rules that callers rely on from the parent abstraction.

Step-by-step example

Let’s start with the classic bird example because it makes the idea instantly visible.

Base class defines an expectation.
If a class is called Bird and it exposes fly(), callers will assume all birds can fly.
A valid subtype keeps that expectation.
Sparrow can inherit from Bird because it does not break the contract.
An invalid subtype breaks the contract.
Penguin inherits Bird but cannot truly support fly().
The caller is now unsafe.
A function written against Bird may crash when passed a Penguin.
The fix is to model behavior more honestly.
Move fly() to a more specific abstraction like FlyingBird. 
class Bird {
  fly() {
    console.log("Flying");
  }
}

class Sparrow extends Bird {}

function makeBirdFly(bird) {
  bird.fly();
}

makeBirdFly(new Sparrow()); // OK
class Bird {
  fly() {
    console.log("Flying");
  }
}

class Penguin extends Bird {
  fly() {
    throw new Error("Penguins can't fly");
  }
}

function makeBirdFly(bird) {
  bird.fly();
}

makeBirdFly(new Penguin()); // Runtime error
Correct refactor

Separate what all birds do from what only some birds do. 

class Bird {
  eat() {
    console.log("Eating");
  }
}

class FlyingBird extends Bird {
  fly() {
    console.log("Flying");
  }
}

class Sparrow extends FlyingBird {}
class Eagle extends FlyingBird {}
class Penguin extends Bird {}

Line-by-line explanation of the important code

Why the bad version fails
  • Bird exposes fly(), so callers trust that behavior.
  • makeBirdFly(bird) depends only on the base abstraction.
  • Penguin extends Bird but cannot honor that contract.
  • So inheritance exists syntactically, but substitution fails semantically.
Why the refactor works
  • Bird only contains behavior shared by all birds.
  • FlyingBird adds the more specific fly() contract.
  • Penguin no longer lies about what it can do.
  • Now each subtype is honest, and callers can trust the abstraction again.

Classic interview example: Rectangle vs Square

This is the most famous LSP example because mathematically a square is a rectangle, but in OOP the behavioral contract often makes that inheritance invalid. 

class Rectangle {
  constructor() {
    this.width = 0;
    this.height = 0;
  }

  setWidth(w) {
    this.width = w;
  }

  setHeight(h) {
    this.height = h;
  }

  getArea() {
    return this.width * this.height;
  }
}

class Square extends Rectangle {
  setWidth(w) {
    this.width = w;
    this.height = w;
  }

  setHeight(h) {
    this.width = h;
    this.height = h;
  }
}

function resize(rectangle) {
  rectangle.setWidth(5);
  rectangle.setHeight(4);
  return rectangle.getArea();
}

console.log(resize(new Rectangle())); // 20
console.log(resize(new Square()));    // 16 -> unexpected
Why this violates LSP

The caller assumes width and height can vary independently because that is what Rectangle promises. Square silently changes that rule.

Common mistakes and confusions

Mistake

“Inheritance is mainly for code reuse.”

Wrong mental model. Inheritance means “is a valid subtype,” not “can reuse some methods.”

Mistake

“If it compiles, LSP is fine.”

LSP is about behavior, not syntax. A design can compile and still violate substitution badly.

Mistake

Adding instanceof checks everywhere.

That often means your base abstraction is not trustworthy.

Mistake

Throwing new unsupported-operation errors in child classes.

If the parent exposes an operation, the child should not suddenly reject it unless the abstraction was wrong.

Complexity

Relevant?

Time and space complexity are not the focus here. LSP is a design principle, not an algorithmic technique.

Real-world use cases

Area Base abstraction Valid substitutes What would break LSP
Payments PaymentProcessor.pay(amount) Stripe, PayPal, BankTransfer A processor that throws for normal valid inputs or changes the expected meaning of pay
Storage Storage.save(data) S3, local disk, database storage A storage implementation that silently discards valid data or cannot honor the base contract
Logging Logger.log(message) ConsoleLogger, FileLogger, CloudLogger A logger that crashes when given messages the base type allows
Backend architecture Repository.getById(id) MongoRepository, InMemoryRepository, PostgresRepository A repository that changes null/error semantics unexpectedly

Comparison with the safer alternative

Composition over inheritance

Many LSP violations happen because inheritance is used where composition would be safer. 

class FlyWithWings {
  fly() {
    console.log("Flying with wings");
  }
}

class NoFly {
  fly() {
    throw new Error("This behavior should not be used");
  }
}

// Better idea: don't force all birds to expose fly at the same level.
// Compose behavior only where it belongs.
Inheritance

Good when the child is truly a valid subtype.

Bad when used only for shared code.

Composition

More flexible and usually safer.

Lets you model behavior honestly without fake subtype relationships.

How LSP connects to other concepts

  • Polymorphism: LSP is what makes polymorphism trustworthy.
  • Inheritance: LSP tells you when inheritance is valid, not just possible.
  • Open/Closed Principle: extension is safer when substitutability holds.
  • Interface design: bad abstractions often lead directly to LSP violations.
  • Composition over inheritance: a frequent fix when inheritance creates dishonest hierarchies.

How this appears in interviews

Classic prompt

“Why is Square extends Rectangle a problem?”

Strong answer: because the child changes assumptions the caller relies on, so the subtype cannot safely replace the base type. That is an LSP violation.

What interviewers usually want to hear

  • LSP is about behavioral substitutability.
  • Inheritance is not just code reuse.
  • A child must respect the parent’s contract.
  • If you need special-case checks for a subtype, your design is probably wrong.

Interview explanation version

30-second answer

Liskov Substitution Principle says that if a class inherits from another, then the child must be usable anywhere the parent is expected without breaking the program. In practice, that means the child must preserve the parent’s contract and behavior. A classic example is Square and Rectangle: if Square changes how width and height behave, then it is not a valid substitute for Rectangle.

Trick questions / trap answers

Trap #1

“But mathematically a square is a rectangle.”

True mathematically. But in OOP the problem is behavioral contract, not category theory.

Trap #2

“Can I just override the method differently?”

Only if the caller’s expectations remain valid. Different code is fine. Broken contract is not.

Trap #3

“Unsupported operation in child is fine.”

Usually that means the base abstraction was wrong or too broad.

Pattern to remember

Ask this every time you use inheritance: 1. Is the child really a subtype? 2. Can I pass the child anywhere the parent is expected? 3. Will the caller still get the behavior it was promised? 4. If not, should I redesign the abstraction or use composition?

Feynman Technique

Explain it like you're 10

Imagine you have a TV remote. Every TV that says it works with that remote should really work. If one TV suddenly breaks when you press the channel button, then it was not truly compatible.

LSP says subclasses should be like that: if they say they are a kind of the parent, they must work properly anywhere the parent is used.

Final takeaway

One sentence to keep

Inheritance is correct only when the child preserves the parent’s behavior, not just its method names.

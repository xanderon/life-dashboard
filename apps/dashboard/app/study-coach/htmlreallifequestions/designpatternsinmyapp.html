1. Problem Statement

↑ Back to chapters
Problem

In interviews, you are often asked something like: "Explain design patterns you used in a real project" or "How do patterns appear in a microservices architecture?"

The challenge is that many candidates know the textbook definitions, but they struggle to connect them to a real system with services, queues, REST calls, controllers, managers, repositories, adapters, and connection pools.

For this study page, the concrete problem is:

Interview-style problem

Given a real microservices environment with services like monitoring, warranty, communication, REST clients, and RabbitMQ consumers, explain:

  • what patterns are present,
  • what real problem each one solves,
  • how it works in practice,
  • and how to explain it clearly in an interview.
Why this matters

This is not a pure LeetCode problem. It is a system design / architecture explanation problem. The interviewer wants to see whether you understand why the architecture was built that way, not only whether you can list pattern names.

2. Examples

↑ Back to chapters

Before going into theory, it helps to anchor everything in real situations.

Example A — Device event flow

A device service updates a device. It should not block while waiting for monitoring, warranty, or communication-related side effects to finish.

So the device service publishes an event, and other services consume it asynchronously.

Example B — Warranty external API differences

A warranty service must talk to external APIs that do not behave the same way in all regions. One region may use a client ID, another may use a token-based flow.

Instead of spreading region-specific if/else logic everywhere, an adapter hides those differences behind a unified interface.

Example C — SMTP auth strategies

A communication service may send email with different authentication modes, for example basic or token.

The sending flow is mostly the same; only the authentication strategy changes.

Example D — Shared DB connection reuse

If every request created a new Mongo connection, the system would waste resources and risk pool exhaustion.

Reusing a shared connection or pool behaves like a Singleton-style resource.

Real Situation Pattern Main Benefit
Device publishes events to RabbitMQ Publisher-Subscriber / Observer Loose coupling and async processing
Controller → Manager → Repository flow Layered Architecture Clear separation of responsibilities
Global vs PRC warranty API differences Adapter Unified interface over different external APIs
Basic auth vs token auth in SMTP Strategy Runtime-swappable behavior
Shared DB pool reuse Singleton-style resource sharing Efficiency and consistency

3. Main Idea / Intuition

↑ Back to chapters
Main intuition

Design patterns are not decoration. They exist because real systems become hard to change, hard to scale, and hard to reason about unless responsibilities are separated and communication is controlled.

The simplest mental model is this:

Mental model

A large microservices system is like a company with departments:

  • Controllers are the reception desk — they receive requests.
  • Managers / services are the decision makers — they apply business rules.
  • Repositories are the archive room — they know how to access stored data.
  • Message queues are the mailroom — services send notifications without direct interruption.
  • Adapters are translators — they make different external systems look uniform.
  • Strategies are interchangeable methods of doing the same job.
  • Singleton-style shared resources are shared utilities, like one managed connection pool.

So the main idea is: patterns reduce chaos. They give structure to communication, responsibility, variation, and reuse.

4. Step-by-Step Walkthrough

↑ Back to chapters

Let’s walk through a realistic scenario from the point of view of the architecture.

Step 1 — A request or event enters the system

A device changes state or an API endpoint is called. The controller or event consumer becomes the entry point.

Step 2 — Business logic is delegated

The controller should not do everything itself. It forwards the request to a manager or service layer. This is where decisions are made.

Step 3 — Data access is delegated again

The service layer should not contain raw DB logic everywhere. Data retrieval or persistence is delegated to repository-like code.

Step 4 — Other services may need to react

Instead of forcing synchronous calls to every interested service, the current service can publish an event through RabbitMQ. Subscribers react independently.

Step 5 — External systems may need translation

If the service talks to an external API with different contracts, an adapter isolates those differences.

Step 6 — Different behaviors may be selected at runtime

If one piece of logic changes depending on configuration, like auth mode or sending mechanism, Strategy keeps that variation clean.

Step 7 — Shared heavy resources are reused

Database connection pools or shared clients are reused rather than recreated, which is why Singleton-style handling often appears.

5. Final JavaScript Solution

↑ Back to chapters

Since this is an interview explanation problem rather than an algorithmic one, the “solution” is best represented as a compact JavaScript model of the architecture. 

// A simplified interview-friendly model of how patterns appear together

class DeviceRepository {
  constructor(db) {
    this.db = db;
  }

  async findById(deviceId) {
    return this.db.devices.find((device) => device.id === deviceId) || null;
  }

  async save(device) {
    const index = this.db.devices.findIndex((d) => d.id === device.id);

    if (index === -1) {
      this.db.devices.push(device);
    } else {
      this.db.devices[index] = device;
    }

    return device;
  }
}

class WarrantyApiAdapter {
  constructor(region) {
    this.region = region;
  }

  async getWarranty(deviceId) {
    if (this.region === "PRC") {
      return this.callTokenBasedApi(deviceId);
    }

    return this.callClientIdBasedApi(deviceId);
  }

  async callTokenBasedApi(deviceId) {
    return {
      deviceId,
      region: "PRC",
      authMode: "token",
      warrantyStatus: "ACTIVE"
    };
  }

  async callClientIdBasedApi(deviceId) {
    return {
      deviceId,
      region: "GLOBAL",
      authMode: "clientId",
      warrantyStatus: "ACTIVE"
    };
  }
}

class BasicSmtpStrategy {
  async getCredentials() {
    return { type: "basic", username: "user", password: "secret" };
  }
}

class TokenSmtpStrategy {
  async getCredentials() {
    return { type: "token", token: "abc123" };
  }
}

class MailService {
  constructor(strategy) {
    this.strategy = strategy;
  }

  async send(message) {
    const credentials = await this.strategy.getCredentials();

    return {
      status: "SENT",
      credentialsType: credentials.type,
      message
    };
  }
}

class EventBus {
  constructor() {
    this.listeners = {};
  }

  subscribe(eventName, handler) {
    if (!this.listeners[eventName]) {
      this.listeners[eventName] = [];
    }

    this.listeners[eventName].push(handler);
  }

  async publish(eventName, payload) {
    const handlers = this.listeners[eventName] || [];

    for (const handler of handlers) {
      await handler(payload);
    }
  }
}

class DeviceManager {
  constructor({ repository, warrantyAdapter, eventBus }) {
    this.repository = repository;
    this.warrantyAdapter = warrantyAdapter;
    this.eventBus = eventBus;
  }

  async processDeviceUpdate(deviceId) {
    const device = await this.repository.findById(deviceId);

    if (!device) {
      throw new Error("Device not found");
    }

    const warranty = await this.warrantyAdapter.getWarranty(deviceId);

    const updatedDevice = {
      ...device,
      warrantyStatus: warranty.warrantyStatus
    };

    await this.repository.save(updatedDevice);

    await this.eventBus.publish("device.updated", {
      deviceId,
      warrantyStatus: warranty.warrantyStatus
    });

    return updatedDevice;
  }
}

// Singleton-style shared DB object
const sharedDb = {
  devices: [
    { id: "d1", name: "ThinkPad-01", warrantyStatus: "UNKNOWN" }
  ]
};

// Wiring everything together
const repository = new DeviceRepository(sharedDb);
const warrantyAdapter = new WarrantyApiAdapter("GLOBAL");
const eventBus = new EventBus();

eventBus.subscribe("device.updated", async (payload) => {
  console.log("Monitoring service received:", payload);
});

eventBus.subscribe("device.updated", async (payload) => {
  console.log("Communication service received:", payload);
});

const manager = new DeviceManager({
  repository,
  warrantyAdapter,
  eventBus
});

manager.processDeviceUpdate("d1").then(console.log);
What this solution shows
  • Repository for data access
  • Adapter for external warranty API differences
  • Strategy for SMTP credential mode
  • Observer / Pub-Sub style event bus for service reactions
  • Layering via manager orchestration
  • Singleton-style shared resource via shared DB instance

6. Line-by-Line Explanation

↑ Back to chapters
Repository

DeviceRepository exists so the rest of the system does not need to know where or how devices are stored.

That means business logic can say findById and save without embedding raw DB details everywhere.

Adapter

WarrantyApiAdapter hides the regional differences in the external API.

The manager just says: getWarranty(deviceId). It does not need to care whether the region uses token auth or client ID auth.

Strategy

BasicSmtpStrategy and TokenSmtpStrategy represent different ways to provide credentials.

The mail service keeps one stable contract while the strategy changes at runtime.

Event Bus

The event bus models the idea that one service publishes and many others can react.

This mirrors Observer / Publisher-Subscriber behavior in a simplified way.

Manager

DeviceManager coordinates the use case: load device, fetch warranty, persist change, publish event.

This is the business layer that connects patterns together.

Shared Resource

sharedDb stands in for a shared connection or pool.

The point is not the variable itself, but the architectural idea: expensive resources should usually be reused, not recreated per request.

7. Pattern-by-Pattern Breakdown

↑ Back to chapters

Microservices Architecture

The system is split into separate services such as monitoring, warranty, and communication. This avoids a single monolith where all concerns are coupled together.

Interview point: if one area needs scaling or deployment, you do not want to redeploy everything else.

Publisher-Subscriber / Event-Driven Architecture

One service publishes an event, and interested consumers react asynchronously. This is ideal when a change in one domain should trigger work elsewhere without blocking the original request.

Loose coupling Async processing Scalable fan-out

Layered Architecture

Controllers handle input. Managers or services handle business logic. Repositories handle persistence. Each layer exists for a different reason.

Interview point: this reduces mixing of HTTP concerns, business rules, and DB code.

Observer

In practice, Observer appears inside the event-driven model: consumers subscribe to changes and react when something happens.

It helps avoid wasteful polling and allows event-based reaction.

Adapter

Adapter is useful when outside systems are inconsistent. You do not want every caller to know all the quirks of every external API.

Instead, one adapter translates the ugly parts into a stable internal contract.

Strategy

Strategy is best when the algorithm or behavior changes, but the overall workflow stays the same.

For example, sending email still means “send mail,” but how credentials are resolved may differ.

Singleton-style Connection Pooling

A shared connection or pool is a practical example of Singleton-like behavior: one managed reusable resource instead of repeated expensive initialization.

8. Common Mistakes

↑ Back to chapters
Mistake 1

Naming patterns without explaining the problem.
Saying “we used Strategy” is weak. Saying “we had multiple auth modes and Strategy let us swap the credential resolution cleanly” is much stronger.

Mistake 2

Confusing architecture with design pattern.
Microservices Architecture is a higher-level architectural style. Adapter or Strategy is a more local design pattern.

Mistake 3

Calling everything a pattern.
Not every piece of code needs a fancy name. The important part is the design reason behind it.

Mistake 4

Ignoring trade-offs.
Event-driven systems reduce coupling, but debugging can become harder. Layering improves structure, but can add more files and indirection.

Mistake 5

Giving only textbook definitions.
Interviews are much stronger when you connect the pattern to a concrete flow: controller → service → repository, publish event, adapter to external API, and so on.

9. Complexity

↑ Back to chapters

This kind of problem is not mainly about Big-O, but there is still a useful way to think about complexity:

Aspect Main Cost Why It Matters
Direct synchronous service calls Latency coupling One service waits for another
Event-driven processing Operational complexity Better decoupling, harder tracing/debugging
Layered architecture Code indirection Clearer boundaries, more files / hops
Adapters Extra abstraction layer Cleaner callers, centralized translation logic
Strategies More objects / types Cleaner variation and extensibility
Singleton-style shared resources Lifecycle management Efficient reuse, but careful initialization required
Interview takeaway

The key “complexity” discussion here is usually not time complexity. It is about maintainability, coupling, scalability, and change cost.

10. Interview Explanation Version

↑ Back to chapters
30-second version

In a real microservices environment, design patterns appear naturally as responses to real problems. For example, we use event-driven Publisher-Subscriber patterns to decouple services, layered architecture to separate controllers, business logic, and persistence, adapters to hide external API differences, strategies when behavior changes by configuration, and shared connection pooling as a Singleton-style resource reuse pattern.

60-second version

The most important thing is not just naming the pattern but explaining the pain it solves. In a microservices system, if services call each other synchronously for every side effect, they become tightly coupled and slower, so event-driven communication helps. Inside each service, controllers should not do DB work directly, so layered separation helps. When an external API differs by region or auth model, Adapter hides that difference. When one workflow has multiple interchangeable behaviors, like auth mode, Strategy keeps it clean. And for expensive resources like DB connections, we reuse shared pools instead of creating them per request.

Good interview structure
  1. Name the pattern.
  2. State the real problem.
  3. Explain how the pattern solves it.
  4. Give one concrete example from service flow.
  5. Mention one trade-off.

11. Pattern to Remember

↑ Back to chapters
Simple formula

Pattern = repeated problem + reusable structure.

When communication hurts

Think Publisher-Subscriber / Observer.

When responsibilities are mixed

Think Layered Architecture.

When external systems differ

Think Adapter.

When one behavior changes by config

Think Strategy.

When heavy resources are reused

Think Singleton-style shared instance.

When the whole system must scale independently

Think Microservices Architecture.

12. Optional Brute Force Comparison

↑ Back to chapters

A good way to understand patterns is to compare them with the messy version.

Brute force / messy version
  • Controller contains business logic
  • Controller queries DB directly
  • Service makes direct synchronous calls everywhere
  • External API differences handled with scattered if/else
  • Auth differences handled inline in the same function
  • New DB connection per request
Pattern-based version
  • Controller only handles input/output
  • Manager handles orchestration
  • Repository handles persistence
  • Event bus handles async reactions
  • Adapter hides external contract differences
  • Strategy swaps behavior cleanly
  • Shared pool reuses connections
Core conclusion

The “pattern solution” is rarely about writing more code. It is about making the codebase easier to extend, safer to change, and easier to explain.

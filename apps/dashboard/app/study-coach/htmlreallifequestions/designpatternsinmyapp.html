Microservices Architecture

↑ Back to top
Design Pattern

Microservices Architecture

Problem Solved

In a monolithic application, all features sit in one codebase. That makes it hard to scale specific parts independently. If warranty processing slows down, the whole application is affected, and even a small change can require restarting everything.

How It Solves It

The system is split into independent services. For example:

  • xc1p-monitoring handles alerts and events
  • xc1p-warranty manages device warranties
  • xc1p-communication sends emails and SMS

Each service has its own database and API and can be deployed or scaled separately.

Location
Overall structure in folders like /Users/xan/Downloads/all-pz/xc1p-monitoring/sourceCode/
Communication Details

Services communicate through REST for synchronous communication and RabbitMQ for asynchronous communication. Example given in the source: xc1p-monitoring can notify xc1p-communication for alerts via events.

Event-Driven Architecture with Message Queues

↑ Back to top
Design Pattern

Publisher-Subscriber (via Message Queues)

Problem Solved

Direct synchronous calls between services create tight coupling and can introduce delays. A device update should not have to wait for multiple other services to process that change, because that increases the risk of timeouts and failures.

How It Solves It

A service publishes events to RabbitMQ and subscribers consume them asynchronously. The source gives the example of xc1p-device publishing events such as device.new, while services like xc1p-monitoring consume those events without blocking the publisher.

Topic routing ensures that only relevant services receive the messages.

RESTful API Communication

↑ Back to top
Design Pattern

RESTful API Communication

Problem Solved

Some services need immediate data from other systems and cannot wait for asynchronous processing. The example from the source is that xc1p-warranty needs translations right away in order to display warranty messages in the user’s language.

How It Solves It

Services use Axios-based HTTP calls to predefined endpoints. Keep-alive agents are used to maintain connections for performance, and retry-oriented error handling helps when calls fail.

Layered Architecture

↑ Back to top
Design Pattern

Layered Architecture (MVC + Repository)

Problem Solved

Mixing HTTP handling, business rules, and database queries in the same place makes the code harder to test, harder to maintain, and more error-prone.

How It Solves It
  • Controllers handle HTTP requests
  • Managers / Services apply business logic
  • Repositories handle database access and indexes

The source specifically mentions this structure in services like xc1p-monitoring and xc1p-communication.

Observer Pattern

↑ Back to top
Design Pattern

Observer Pattern (Embedded in Event-Driven)

Problem Solved

Services should react to changes when they happen, instead of constantly polling and wasting resources. The source uses the example that xc1p-monitoring should not repeatedly check whether devices changed.

How It Solves It

Services register as observers through RabbitMQ consumers. When xc1p-device publishes a change, observer services are notified automatically and process it in parallel workers.

Location
/Users/xan/Downloads/all-pz/xc1p-monitoring/sourceCode/services/devices.consumer.js — lines 125-135
Communication Details

The source describes xc1p-device as the publisher, and services like xc1p-monitoring and xc1p-warranty as observers reacting to those changes.

Adapter Pattern

↑ Back to top
Design Pattern

Adapter Pattern

Problem Solved

External APIs can expose different interfaces. The file gives the example of Lenovo’s warranty API: global regions and PRC use different authentication models. Without adaptation, the code would need scattered conditional logic.

How It Solves It

Adapters wrap the differences. The source mentions:

  • RunConfig for global usage with client ID
  • RunConfigPRC for PRC with token-based access

The rest of the code interacts through one unified interface.

Location
/Users/xan/Downloads/all-pz/xc1p-warranty/sourceCode/services/warranty.external.js — lines 15-30
Communication Details

This pattern is used inside xc1p-warranty to adapt calls to the external Lenovo warranty APIs. The source explicitly notes that this is not inter-service communication.

Strategy Pattern

↑ Back to top
Design Pattern

Strategy Pattern

Problem Solved

Some behaviors vary based on configuration, but the overall workflow stays the same. The example in the source is SMTP authentication in xc1p-communication, where different auth modes may be needed.

How It Solves It

Different strategies are selected at runtime. The source example says:

  • If authType = basic, fetch password
  • If authType = token, fetch token value

This keeps the core sending logic clean while allowing behavior to vary by config.

Communication Details

This is described as internal to xc1p-communication. The source also mentions that it uses SecretsUtils for secure data retrieval.

Singleton Pattern

↑ Back to top
Design Pattern

Singleton Pattern (via Connection Pooling)

Problem Solved

Creating a new database connection for every request wastes resources and increases the risk of pool exhaustion. The document gives the example that alert queries in xc1p-monitoring could overload MongoDB if each query created a separate connection.

How It Solves It

A shared connection pool is reused inside the service. The pool has a configured max size and idle timeout, so requests reuse existing connections instead of creating new ones.

Location
/Users/xan/Downloads/all-pz/xc1-nodejs-utils/lib/db/mongo-db-tenant.manager.js — lines 25-35
Communication Details

This is internal to each service. The example given is that xc1p-monitoring reuses the shared pool through its database manager instead of opening a new connection on every alert query.

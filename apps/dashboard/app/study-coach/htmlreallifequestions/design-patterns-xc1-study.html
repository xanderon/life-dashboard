Document Complet: Design Patterns și Principii de Design în Aplicația XC1

Introducere

Acest document prezintă analiza completă a design patterns-urilor, architectural patterns-urilor și principiilor de design implementate în aplicația XC1. Sistemul constă în peste 30 de microservicii independente pentru managementul dispozitivelor IoT, folosind Node.js, Go, și diverse baze de date.

Analiza se bazează pe examinarea codului sursă din folderele xc1-nodejs-utils, xc1-golang-utils, și microserviciile individuale precum xc1p-device, xc1p-monitoring, etc.

1. Microservices Architecture

2. Categoria

Architectural Pattern

3. Conceptul pe scurt

Arhitectură în care aplicația este împărțită în servicii mici, independente, care comunică între ele prin API-uri sau mesaje.

4. Cum este implementat în proiect

Întreaga structură a proiectului este organizată în microservicii separate: xc1p-device, xc1p-organizations, xc1p-communications, xc1p-monitoring, etc. Fiecare serviciu rulează în propriul container Docker cu porturi dedicate (8080/8443). În xc1p-device/sourceCode/server.js, serviciul se inițializează independent cu propriul database manager și controller.

5. Exemplu concret din aplicație

async function init() {
    await WebServerManager.start(_context);
    await DatabaseManager.init(_context);
    await DevicesController.init(_context);
    Probes.EventEmitter.emit(Probes.EventEmitter.Constants.ServiceStarted, _context);
}

Fiecare microserviciu are propriul lifecycle, configurație și scalare independentă.

6. De ce este util în acest sistem

Permite scalarea independentă a serviciilor (ex: scalezi doar xc1p-device când ai trafic mare), dezvoltarea paralelă de către echipe diferite, și toleranță la defecte (căderea unui serviciu nu oprește sistemul). Suportă tehnologii mixte (Java, Go, Node.js).

7. Cum aș explica acest lucru la interviu

"În aplicația XC1 folosim microservicii pentru că avem 30+ servicii independente - fiecare cu propria bază de date și API. De exemplu, serviciul device gestionează dispozitivele IoT, iar organizations gestionează organizațiile. Comunică prin REST și RabbitMQ, permițând scalare independentă și dezvoltare paralelă."

2. Event Driven Architecture

2. Categoria

Architectural Pattern

3. Conceptul pe scurt

Arhitectură în care componentele reacționează la evenimente în loc să apeleze direct alte componente.

4. Cum este implementat în proiect

Implementat prin RabbitMQ cu exchange-uri topic și headers în xc1-nodejs-utils/lib/servicesUtils/rmq.utils.js și xc1-nodejs-utils/lib/servicesUtils/monitoring.service.utils.js. Serviciile publică evenimente pe exchange-ul XC1-Monitoring cu topic-uri precum device.connected, device.modified, etc.

5. Exemplu concret din aplicație

const PrivateConstants = {
    RMQ: {
        TopicExchange: `XC1-Monitoring`,
        HeadersExchange: `XC1-Monitoring-headers`,
        ExchangeType: {
            Topic: `topic`,
            Headers: `headers`
        },
    },
    Action: {
        New: `new`,
        Modified: 'modified',
        Recovered: `recovered`,
        Removed: `removed`,
    },
};

Flux real: Device event → RabbitMQ exchange → monitoring service → alert creation → communication service.

6. De ce este util în acest sistem

Decuplează producătorii de consumatori, permite scalarea orizontală, și asigură reziliență (mesajele persistă dacă un consumator cade). Suportă procesare asincronă pentru evenimente IoT.

7. Cum aș explica acest lucru la interviu

"Arhitectura event-driven înseamnă că când un dispozitiv IoT se conectează, trimite un eveniment pe RabbitMQ exchange. Serviciile de monitoring, warranty și communications ascultă evenimente relevante fără să știe cine le-a trimis, permițând scalare independentă."

3. Publisher/Subscriber Pattern

2. Categoria

Integration / Communication Pattern

3. Conceptul pe scurt

Pattern în care publisher-ii trimit mesaje către un intermediar, iar subscriber-ii primesc mesaje relevante fără cunoașterea publisher-ului.

4. Cum este implementat în proiect

În xc1-nodejs-utils/lib/servicesUtils/rmq.utils.js cu metode Exchange.produce() pentru publicare și Exchange.consume() pentru consum. Folosește topic routing pentru filtrarea mesajelor și confirmări de livrare.

5. Exemplu concret din aplicație

// PUBLISH
await channel.assertExchange(exchangeName, exchangeType, options.exchange);
await channel.publish(
    exchangeName,
    topic,
    message2buffer(data),
    options.message || { persistent: false },
);

// SUBSCRIBE
const channel = await RMQService.createChannel(_context);
const queue = await channel.assertQueue(queueName, options.queue);
await channel.bindQueue(queue.queue, exchangeName, topic);
channel.consume(queue.queue, async (msg) => {
    await callback(JSON.parse(msg.content.toString()), _context);
    channel.ack(msg);
}, { noAck: options.noAck, prefetch: options.prefetch });

6. De ce este util în acest sistem

Permite unu-la-mulți (un eveniment notifică mai mulți consumatori) și decuplare completă între publisher și subscriber. Suportă prefetch pentru controlul ratei de procesare.

7. Cum aș explica acest lucru la interviu

"Publisher/Subscriber înseamnă că serviciul device publică evenimente pe RabbitMQ fără să știe cine le consumă. Serviciul monitoring abonează la 'device.*' și primește toate evenimentele dispozitivelor, fără cuplare directă."

4. Message Queue Pattern

2. Categoria

Integration / Communication Pattern

3. Conceptul pe scurt

Pattern care folosește cozi pentru a decupla producătorii de consumatori, permițând procesare asincronă.

4. Cum este implementat în proiect

Implementat în xc1-nodejs-utils/lib/queue/message.repository.js și xc1-nodejs-utils/lib/queue/local.queue.js cu persistare locală pentru backup, retry logic (max 3 încercări), și status tracking.

5. Exemplu concret din aplicație

const queue = {
    id: generatedQueueId,
    messages: [],
    
    publish: (message) => {
        queue.messages.push({
            id: uuid(),
            payload: message,
            timestamp: Date.now(),
            retryCount: 0,
            status: 'pending'
        });
    },
    
    consume: async (callback) => {
        while (queue.messages.length > 0) {
            const message = queue.messages.shift();
            try {
                await callback(message.payload);
                message.status = 'processed';
            } catch (error) {
                message.retryCount++;
                if (message.retryCount < 3) {
                    queue.messages.push(message);
                }
            }
        }
    }
};

6. De ce este util în acest sistem

Asigură că mesajele nu se pierd dacă consumatorii cad, permite throttling (limitare rată procesare), și distribuie load-ul între mai mulți workeri. Backup-ul local oferă reziliență suplimentară.

7. Cum aș explica acest lucru la interviu

"Message Queue pattern înseamnă că evenimentele dispozitivelor intră într-o coadă RabbitMQ. Dacă serviciul monitoring cade, mesajele așteaptă. Când revine, procesează toate mesajele în ordine, cu retry pentru cele eșuate."

5. REST Service-to-Service Communication

2. Categoria

Integration / Communication Pattern

3. Conceptul pe scurt

Serviciile comunică prin HTTP REST API-uri cu metode standard (GET, POST, etc.).

4. Cum este implementat în proiect

În xc1-nodejs-utils/lib/generalUtils/rest.client.js și rest-services.js cu service registry centralizat, conexiuni HTTPS cu certificate mTLS, și keep-alive pentru reutilizarea conexiunilor.

5. Exemplu concret din aplicație

const PrivateConstants = {
    Services: {
        Organizations: {
            host: `xc1p-organizations`,
            prefix: `organizations-management`,
            port: 8080,
            sPort: 8443,
        },
        Communications: {
            host: `xc1p-communications`,
            prefix: `communications`,
            port: 8080,
            sPort: 8443,
        }
    }
};

// HTTP Request cu Keep-Alive
const httpsOptions = {
    cert: pem,
    key: key,
    ca: CommunicationUtils.Certificates.CA.getS2SRoot(),
};
options.httpsAgent = new https.Agent(httpsOptions);

6. De ce este util în acest sistem

Comunicare sincronă pentru date imediate, service discovery centralizat, și securitate prin mTLS între servicii. Keep-alive optimizează performanța.

7. Cum aș explica acest lucru la interviu

"Serviciile comunică prin REST API-uri securizate cu mTLS. Când monitoring-ul detectează o problemă, apelează GET către organizations pentru a obține contextul organizației, apoi trimite alertă personalizată."

6. Layered Architecture

2. Categoria

Application Design Pattern

3. Conceptul pe scurt

Arhitectură cu straturi separate: presentation, business logic, data access, fiecare cu responsabilități clare.

4. Cum este implementat în proiect

În fiecare microserviciu: routes → controllers → managers/services → repositories → database. Exemplu în xc1p-device/sourceCode/ cu separarea clară între router, controller, manager și database access.

5. Exemplu concret din aplicație

Routes Layer: router.route(`${GlobalConstants.DEVICE_PATH}/`).get(DevicesController.getAll);
Controller Layer: async getAll(req, res, next) { validation + call manager }
Manager Layer: getAll: async (req, attributes, _context) => { business logic }
Repository Layer: MongoDAO.FindAll() → database query

6. De ce este util în acest sistem

Separă responsabilitățile: controllers validează request-uri, managers conțin logică business, repositories accesează date. Ușurează testarea și întreținerea.

7. Cum aș explica acest lucru la interviu

"Layered architecture înseamnă că un request HTTP trece prin router → controller (validare) → manager (logic business) → repository (date). În XC1, controller-ul validează input-ul, manager-ul decide ce date să aducă, iar repository-ul face query-ul MongoDB."

7. Repository Pattern

2. Categoria

Application Design Pattern

3. Conceptul pe scurt

Abstracție care ascunde detaliile de persistență a datelor în spatele unei interfețe uniforme.

4. Cum este implementat în proiect

În xc1-golang-utils/database/mongodb/base_dao.go cu metode FindOne(), FindAll(), InsertOne() care încapsulează query-urile MongoDB, timeout-uri, și audit trail automat.

5. Exemplu concret din aplicație

func (dao *MongoDAO) FindOne(hubctx *hubcontext.Context, mongoCollection MongoCollection, 
                             filter map[string]interface{}, 
                             options ...*mongoOptions.FindOneOptions) (*mongo.SingleResult, error) {
    ctx, cancel := context.WithTimeout(context.Background(), mongoCollection.Timeout)
    defer cancel()
    
    filter = buildMongoFilter(filter)
    return mongoCollection.Collection.FindOne(ctx, filter, options...), nil
}

6. De ce este util în acest sistem

Abstracție peste baza de date permite schimbarea de la MongoDB la altceva fără impact asupra serviciilor, și adaugă funcționalități comune ca audit trail și timeout management.

7. Cum aș explica acest lucru la interviu

"Repository pattern înseamnă că serviciile apelează deviceRepo.FindAll(filter) fără să știe că e MongoDB. Repository-ul încapsulează query-urile, audit trail-ul, și timeout-urile, permițând schimbarea bazei de date fără modificări în business logic."

8. Adapter Pattern

2. Categoria

Application Design Pattern

3. Conceptul pe scurt

Pattern care permite obiectelor cu interfețe incompatibile să lucreze împreună prin adaptarea interfeței.

4. Cum este implementat în proiect

În xc1p-configurations-orchestrator/sourceCode/services/pool/record.js cu clasa Record care standardizează obiecte din surse diferite, adăugând tags pentru căutare și mixin pentru unificare.

5. Exemplu concret din aplicație

class Record {
    constructor(params) {
        this._obj = {}
        if (params) {
            this.mixin(params)
        }
    }

    static newRecord(params, isAdapter) {
        let rec = new Record();
        rec._obj = params;
        rec.isAdapter = isAdapter;
        
        // Standardizează pentru căutare
        if (!rec._obj._tags) rec._obj._tags = {}
        rec._obj._path.split(constants.pathSeparator).forEach(x => rec._obj._tags[x] = 1)
        
        return rec
    }

    mixin(o) {
        Object.assign(this._obj, o)
    }
}

6. De ce este util în acest sistem

Permite integrarea cu sisteme externe fără modificarea codului lor, și normalizează datele pentru procesare uniformă în orchestrator.

7. Cum aș explica acest lucru la interviu

"Adapter pattern înseamnă că când primim date din surse diferite (JSON vs XML), folosim un adapter care le transformă în același format Record. Astfel, codul de procesare nu trebuie să știe sursa datelor."

9. Strategy Pattern

2. Categoria

Application Design Pattern

3. Conceptul pe scurt

Pattern care permite selectarea algoritmului la runtime prin încapsularea algoritmilor într-o familie de clase.

4. Cum este implementat în proiect

În xc1-nodejs-utils/lib/generalUtils/caches/caches.utils.js cu strategii diferite de caching: InMemory, Centralized, TimedCache, selectabile la runtime.

5. Exemplu concret din aplicație

const PublicMethods = {
    createCache: async (options, _context) => {
        switch (options.type) {
            case Constants.Types.InMemory:
                return InMemoryCache.InMemoryCache.createCache(options, _context);
            case Constants.Types.Centralized:
                return CentralizedCache.CentralizedCache.createCache(options, _context);
            case Constants.Types.TimedCache:
                // implementare
        }
    }
}

6. De ce este util în acest sistem

Permite schimbarea comportamentului caching-ului fără modificare codului care-l folosește, și ușurează testarea cu diferite strategii.

7. Cum aș explica acest lucru la interviu

"Strategy pattern pentru caching înseamnă că același cod poate folosi InMemoryCache sau CentralizedCache prin simpla schimbare a parametrului 'type'. La runtime selectăm strategia potrivită fără if-else chains."

10. Observer Pattern

2. Categoria

Application Design Pattern

3. Conceptul pe scurt

Pattern în care un obiect (subject) notifică automat obiectele dependente (observers) când starea sa se schimbă.

4. Cum este implementat în proiect

În xc1-nodejs-utils/lib/express/probes.js cu EventEmitter pentru evenimente lifecycle, și în devices.service.utils.js pentru evenimente business.

5. Exemplu concret din aplicație

// EventEmitter ca subject
const Probes = {
    EventEmitter: new (require('events').EventEmitter)(),
    Constants: {
        ServiceStarted: 'service.started',
        ServiceStopped: 'service.stopped',
    }
};

// Emit eveniment
Probes.EventEmitter.emit(Probes.Constants.ServiceStarted, _context);

// Multipli observers
Probes.EventEmitter.on('service.started', (_context) => {
    log.info('Service started!', _context);
});

6. De ce este util în acest sistem

Permite unu-la-mulți fără cuplare strânsă, și adaugă funcționalități noi (ca health checks) fără modificare codului existent.

7. Cum aș explica acest lucru la interviu

"Observer pattern înseamnă că când serviciul pornește, emite evenimentul 'service.started'. Mai mulți listeners (health checker, metrics collector) primesc notificarea fără ca starter-ul să știe de ei."

11. Singleton Pattern

2. Categoria

Resource / Infrastructure Pattern

3. Conceptul pe scurt

Pattern care asigură că o clasă are o singură instanță și oferă un punct global de acces la ea.

4. Cum este implementat în proiect

În common-utils/xc1-golang-utils/webserver/middleware/context.go cu sync.Once pentru inițializare thread-safe a context-ului global și pool de contexte.

5. Exemplu concret din aplicație

var once sync.Once
var singletonContext *HubContext.ContextProxy
var activeRequests int = 0

func ContextMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        once.Do(func() {
            singletonContext = HubContext.NewContextProxy()
        })
        
        hubContext := contextParser(c.Request)
        c.Set(HubContext.HubContextKeyString, hubContext)
        c.Next()
        
        // Pool context-urile pentru refolosire
        singletonContext.PutContextToPool(hubContext)
    }
}

6. De ce este util în acest sistem

Eficient pentru resurse globale ca configurație sau connection pools, evitând crearea multiplă de instanțe și overhead.

7. Cum aș explica acest lucru la interviu

"Singleton pattern înseamnă că context-ul aplicației se creează o singură dată cu sync.Once, apoi toți request-urile îl refolosesc. Evităm overhead-ul creării context-ului la fiecare request HTTP."

12. Connection Pooling

2. Categoria

Resource / Infrastructure Pattern

3. Conceptul pe scurt

Tehnică de management al conexiunilor pentru reutilizarea lor în loc de creare/distrugere repetată.

4. Cum este implementat în proiect

În xc1-nodejs-utils/lib/db/mongo-db-tenant.manager.js cu cache de conexiuni MongoDB, limite MaxPoolSize=3, MaxConnecting=2, și MaxIdleTimeSec pentru cleanup.

5. Exemplu concret din aplicație

const PrivateConstants = {
    MaxPoolSize: parseInt(process.env.DB_CONN_POOL_SIZE) || 3,
    MaxConnecting: parseInt(process.env.DB_CONN_POOL_SIZE) || 2,
    MaxIdleTimeSec: MaxIdleTimeSec,
};

const client: async (_context, dbName, config) => {
    // GET din cache FIRST
    let conn = CacheUtils.getCachedDatabaseConnection(cacheConfig);
    if (conn) {
        return { client: conn.client, isFromCache: true };
    }
    
    // Creează doar dacă nu există
    const client = await DBUtils.mongodbConnect_v1(config, _context);
    CacheUtils.cacheDatabaseConnection(cacheConfig, client);
    
    return { client, isFromCache: false };
}

6. De ce este util în acest sistem

Îmbunătățește performanța prin evitarea overhead-ului de conectare, și controlează resursele serverului cu limite de pool. Metrics pentru monitorizare.

7. Cum aș explica acest lucru la interviu

"Connection pooling înseamnă că în loc să ne conectăm la MongoDB la fiecare query, păstrăm conexiunile într-un pool cu MaxPoolSize=3. Reutilizăm conexiunile existente, reducând latența de la 100ms la 1ms."

13. Single Responsibility Principle (SRP)

2. Categoria

Design Principles (SOLID / DRY etc.)

3. Conceptul pe scurt

Fiecare clasă/modul ar trebui să aibă o singură responsabilitate și un singur motiv de schimbare.

4. Cum este implementat în proiect

Fiecare fișier are o singură responsabilitate: web-service.js pentru HTTP server, mongo-dao.go pentru data access, rest.client.js pentru HTTP calls, rmq.utils.js pentru RabbitMQ.

5. Exemplu concret din aplicație

RESPONSIBILITY 1: Web Server management
├─ WebService (start(), setupMiddleware(), configRoutes())

RESPONSIBILITY 2: Data Access
├─ MongoDAO (FindOne(), FindAll(), InsertOne())

RESPONSIBILITY 3: Business Logic
├─ DevicesManager (getAll(), getOne())

RESPONSIBILITY 4: HTTP Communication
├─ RestClient (makeCall(), setupHttpsAgent())

6. De ce este util în acest sistem

Ușurează testarea (fiecare componentă separat), întreținerea (schimbări localizate), și reutilizarea (module independente).

7. Cum aș explica acest lucru la interviu

"SRP înseamnă că fiecare fișier are o singură responsabilitate. De exemplu, DevicesController validează doar request-uri HTTP, DevicesManager conține doar logică business, iar MongoDAO face doar query-uri - niciodată amestecate."

14. DRY (Don't Repeat Yourself)

2. Categoria

Design Principles (SOLID / DRY etc.)

3. Conceptul pe scurt

Principiu care spune să nu duplici cod - extrage logica comună în funcții/utilitare reutilizabile.

4. Cum este implementat în proiect

Prin librăriile comune xc1-nodejs-utils și xc1-golang-utils folosite de toate microserviciile pentru logging, REST calls, database access, RabbitMQ, etc.

5. Exemplu concret din aplicație

// În toate serviciile
const log = require('@xc1/xc1-nodejs-utils/lib/generalUtils/log.utils');
const RESTUtils = require('@xc1/xc1-nodejs-utils/lib/generalUtils/rest.utils');
const RMQUtils = require('@xc1/xc1-nodejs-utils/lib/servicesUtils/rmq.utils');
const DevicesUtils = require('@xc1/xc1-nodejs-utils/lib/servicesUtils/devices.service.utils');

// Utilitare comune
xc1-nodejs-utils/
├─ lib/generalUtils/log.utils.js (logging consistent)
├─ lib/generalUtils/rest.client.js (HTTP calls securizate)
├─ lib/servicesUtils/rmq.utils.js (RabbitMQ standardizat)
├─ lib/db/mongo-db-tenant.manager.js (MongoDB multi-tenant)

6. De ce este util în acest sistem

Reduce duplicarea codului între 30+ servicii, ușurează întreținerea (fix bug o dată), și asigură consistență în toată platforma.

7. Cum aș explica acest lucru la interviu

"DRY înseamnă că în loc să scriem același cod de logging în fiecare din cele 30 de microservicii, avem un utilitar comun log.utils.js. Când fixăm un bug în logging, se repară în toată platforma automat."

15. Loose Coupling

2. Categoria

Design Principles (SOLID / DRY etc.)

3. Conceptul pe scurt

Principiu care promovează dependențe slabe între componente, permițând schimbări independente.

4. Cum este implementat în proiect

Prin comunicare event-driven cu RabbitMQ și REST APIs în loc de apeluri directe între servicii. Niciun serviciu nu importă direct alt serviciu.

5. Exemplu concret din aplicație

// LOOSE COUPLING - prin evenimente
RMQUtils.Exchange.produce(
    { deviceId: '123', status: 'online' },
    'XC1-Monitoring',
    'topic',
    'device.connected'
);

// ANTI-PATTERN - TIGHT COUPLING
// const deviceService = require('../xc1p-device');
// deviceService.getDevice(id); // Nu facem asta!

6. De ce este util în acest sistem

Permite înlocuirea sau actualizarea unui serviciu fără impact asupra altora, și ușurează testarea cu mock-uri.

7. Cum aș explica acest lucru la interviu

"Loose coupling înseamnă că serviciul device trimite evenimente pe RabbitMQ fără să știe cine le consumă. Serviciul monitoring poate fi înlocuit cu unul nou fără ca device să fie afectat - doar schimbăm consumer-ul."

16. Separation of Concerns

2. Categoria

Design Principles (SOLID / DRY etc.)

3. Conceptul pe scurt

Principiu care separă diferite aspecte ale unui program în secțiuni distincte care se ocupă de preocupări separate.

4. Cum este implementat în proiect

Prin layered architecture: HTTP routing separat de business logic, business logic separat de data access, validation separat de processing.

5. Exemplu concret din aplicație

// CONTROLLER - SEPARATION: validează input
const DevicesController = {
    async getAll(req, res, next) {
        const validation = Validators.Query.validate(req.query);
        if (validation.error) {
            return RESTUtils.respondWithError(res, validation.error);
        }
        
        const data = await DevicesManager.getAll(req, attributes, _context);
        return RESTUtils.respond(res, data);
    }
};

// MANAGER - SEPARATION: business logic
const DevicesManager = {
    getAll: async (req, attributes, _context) => {
        const config = await Utils.getConfig('getAll', _context);
        const r = await DBUtils.getAllForReq(req, attributes, config, _context);
        return r;
    }
};

// REPOSITORY - SEPARATION: data access
const DBs = {
    Devices: {
        collection: async (_context) => {
            return await MongoDBUtils.collection(
                Constants.DataBases.Collections.Devices, 
                _context
            );
        }
    }
};

6. De ce este util în acest sistem

Permite modificări localizate (schimbarea bazei de date afectează doar repository), testare independentă, și claritate în cod.

7. Cum aș explica acest lucru la interviu

"Separation of concerns înseamnă separarea HTTP handling-ului de business logic. Controller-ul validează request-ul, manager-ul decide ce date să aducă, iar repository-ul face query-ul - fiecare strat are propria preocupare."

Flow-uri Reale din Sistem

1. Runtime pentru evenimente dispozitiv (Event-Driven Flow):

  1. Dispozitiv IoT se conectează la platformă
  2. xc1p-device service detectează conexiunea și publică eveniment pe exchange XC1-Monitoring cu topic device.connected
  3. xc1p-monitoring service consumă evenimentul și creează alertă de conectare
  4. xc1p-warranty service consumă același eveniment și actualizează statusul garanției dispozitivului
  5. xc1p-communications service primește alertă și trimite notificare push/email către utilizator

2. Runtime pentru comunicare REST între servicii:

  1. xc1p-monitoring detectează o anomalie la un dispozitiv
  2. Apelează GET /organizations-management/orgs/{orgId} către xc1p-organizations pentru a obține contextul organizației
  3. xc1p-organizations returnează datele organizației (nume, contacte, setări)
  4. xc1p-monitoring îmbogățește alerta cu informații organizaționale
  5. Apelează POST /communications/notifications către xc1p-communications pentru a trimite alertă personalizată

3. Runtime pentru utilizarea utilitarelor comune:

  • Logging: Toate serviciile folosesc log.utils.js pentru logging consistent cu niveluri și formatare standardizată
  • RabbitMQ: rmq.utils.js oferă API uniform pentru publish/consume în toate serviciile event-driven
  • Database: mongo-db-tenant.manager.js gestionează conexiunile multi-tenant pentru toate serviciile cu MongoDB
  • REST Client: rest.client.js cu keep-alive și mTLS pentru toate apelurile între servicii

Utilitare Comune și DRY

De ce există utilitare comune:

Utilitarele comune (xc1-nodejs-utils, xc1-golang-utils) rezolvă problema duplicării codului între cele 30+ microservicii. În loc să implementeze fiecare serviciu propriul logging, RabbitMQ, sau database access, toate folosesc aceleași utilitare.

Ce problemă rezolvă:

  • Consistență: Toate serviciile au același comportament (ex: logging format)
  • Întreținere: Bug fix în log.utils.js repară logging-ul în toată platforma
  • Productivitate: Dezvoltatorii nu rescriu cod comun
  • Standarde: API-uri uniforme pentru operații comune

Cum ajută la DRY:

// În loc să scrie același cod în fiecare serviciu:
const amqp = require('amqplib');
const conn = await amqp.connect('amqp://localhost');
const channel = await conn.createChannel();

// Folosesc utilitarul comun:
const RMQUtils = require('@xc1/xc1-nodejs-utils/lib/servicesUtils/rmq.utils');
await RMQUtils.Exchange.produce(message, exchange, 'topic', topic);

Implementări Interesante (Design Decisions)

1. Connection Reuse (Keep-Alive):

În rest.client.js, conexiunile HTTPS se păstrează deschise cu keep-alive, reducând latența de la ~50ms la ~5ms pentru request-uri consecutive către același serviciu.

2. Channel Reuse în RabbitMQ:

În rmq.utils.js, canalele RabbitMQ se creează o dată și se reutilizează pentru mai multe operații, evitând overhead-ul de creare/distrugere la fiecare mesaj.

3. Caching Multi-Level:

În caches.utils.js, același API suportă caching în memorie locală, caching distribuit (Redis), sau caching cu expirare automată, selectabil la runtime prin strategy pattern.

4. Concurrency Control:

În mongo-db-tenant.manager.js, pool-ul de conexiuni limitează conexiunile simultane (MaxPoolSize=3), prevenind supraîncărcarea bazei de date. Include și MaxIdleTimeSec pentru cleanup automat.

5. Audit Trail Automat:

În base_dao.go, fiecare operație de scriere în MongoDB generează automat audit trail cu cine, când, și ce s-a schimbat, fără cod suplimentar în servicii.

6. Context Pooling:

În middleware-ul Go, context-urile HTTP se pool-ează pentru refolosire, reducând alocările de memorie și GC pressure în servicii cu trafic mare.

Concluzie

Aplicația XC1 demonstrează implementarea avansată a multiple design patterns și principii într-un sistem de microservicii scalabil pentru IoT. Combinația de event-driven architecture cu REST communication, layered architecture cu repository pattern, și aplicarea consecventă a principiilor SOLID/DRY creează un sistem robust, întreținut și scalabil.

Pentru interviuri, accentul ar trebui pus pe cum aceste patterns rezolvă probleme reale de scalabilitate, întreținere și decoupling în contexte enterprise cu sute de dispozitive IoT.

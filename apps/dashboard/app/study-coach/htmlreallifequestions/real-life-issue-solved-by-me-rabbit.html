Interview-Ready Engineering Case Study

RabbitMQ Channel Exhaustion Issue – Root Cause, Investigation, and Fix

A production-style scalability problem discovered during pre-prod / UAT scale testing in xc1p-monitoring, traced to RabbitMQ channel lifecycle misuse inside a shared utility, then fixed through channel reuse, synchronization, idle cleanup, and safer resource management.

1. Problem Statement

What was happening?

In pre-prod / UAT scale testing, we observed a large number of RabbitMQ publishing failures in xc1p-monitoring. The visible symptom in logs was:

2. Context

Why this was a real scale problem, not just a random log error

This only became obvious under heavy scale conditions. At low traffic, the code “worked,” so the design flaw stayed mostly hidden. But once many devices started sending events at the same time, the system began creating and closing RabbitMQ channels at a very high rate.

The issue was not that RabbitMQ publish itself was broken. The issue was that the application was treating channels like throwaway objects per message, instead of reusable communication paths.

Incoming event burst ↓ xc1p-updates sends many monitoring events ↓ xc1p-monitoring publishes to RabbitMQ ↓ shared utility opens & closes channels per publish ↓ channel churn explodes under concurrency ↓ broker pressure + publish failures + noisy logs
3. Root Cause

The actual technical issue

The root cause was inside the shared RabbitMQ utility: xc1-nodejs-utils/lib/servicesUtils/rmq.utils.js, specifically in PrivateMethods.Exchange.produce().

The original implementation effectively did this for every single publish:

async function produce(exchange, routingKey, message, useConfirmChannel = false) {
  const channel = useConfirmChannel
    ? await RMQService.createConfirmChannel()
    : await RMQService.createChannel();

  channel.publish(exchange, routingKey, Buffer.from(JSON.stringify(message)));

  await channel.close();
}

That means every message incurred full channel lifecycle cost: create → publish → close.

Why this is wrong conceptually

RabbitMQ channels are meant to be lightweight but long-lived. They should usually be created once and reused for many publish operations.

4. Real Example

What happened at scale

Imagine xc1p-updates sends 10,000 events in a short interval. With the old implementation, that translates into:

Operation Per message Total for 10,000 events
Create channel 1 10,000
Publish message 1 10,000
Close channel 1 10,000

So the system was not only doing 10,000 publishes. It was also doing 10,000 channel creations and 10,000 channel closes. That is a huge amount of unnecessary churn.

Old model: publish #1 → createChannel() → publish() → close() publish #2 → createChannel() → publish() → close() publish #3 → createChannel() → publish() → close() ... publish #10000 → createChannel() → publish() → close()
5. Why It Failed

Failure mechanics under concurrency

1. Channel exhaustion

RabbitMQ brokers still have practical limits around channel count, channel creation rate, and resource pressure. When many concurrent publishes all try to create fresh channels, the broker gets overloaded by management overhead, not just business traffic.

2. Socket and protocol churn

Even if channels are cheaper than full TCP connections, creating and tearing them down repeatedly still creates protocol, broker, and event loop overhead. This introduces avoidable pressure on the system.

3. Concurrent duplicate creation

Multiple publish calls arriving at the same time had no synchronization around channel creation. So instead of one reusable channel being created and shared, many channels could be created simultaneously for the same purpose.

4. Unnecessary latency per publish

Each message paid setup and teardown cost. That overhead might be invisible for a few messages, but it becomes significant when traffic spikes.

6. Investigation Walkthrough

How the issue was identified step by step

  1. Scale testing in pre-prod / UAT triggered large traffic bursts.
  2. We noticed repeated RabbitMQ publish failures in logs.
  3. OpenSearch analysis showed the main concentration around POST /api/v1/monitoring/events.
  4. Traffic source analysis pointed mainly to xc1p-updates sending many events.
  5. We traced the publish path down into the shared RMQ utility.
  6. Code review revealed that every publish was creating and closing a channel.
  7. That explained why the issue appeared specifically under concurrency and scale.
Key engineering insight: the functional code path was correct, but the resource lifecycle strategy was not scalable.
7. Main Idea / Intuition

The smarter design

The fix was to stop treating RabbitMQ channels as disposable per-message objects and instead treat them like reusable shared resources.

Correct model: create channel once ↓ reuse for many publishes ↓ refresh idle timer on each use ↓ close only when truly unused or invalid

This is very similar to how we think about database connections or HTTP keep-alive connections: create once, reuse many times, clean up safely when idle or broken.

8. Final JavaScript Solution

Representative implementation idea

const publishChannelCache = new Map();
const publishCreationPromises = new Map();

const PUBLISH_CHANNEL_IDLE_TIMEOUT_MS = 15 * 60 * 1000;

function getCacheKey(useConfirmChannel) {
  return useConfirmChannel
    ? "rmq-publish:confirm"
    : "rmq-publish:channel";
}

async function evictCachedPublishChannel(cacheKey) {
  const cached = publishChannelCache.get(cacheKey);
  if (!cached) return;

  publishChannelCache.delete(cacheKey);

  try {
    clearTimeout(cached.idleTimer);
    await cached.channel.close();
  } catch (err) {
    // Ignore close errors during cleanup
  }
}

function scheduleIdleEviction(cacheKey, cachedEntry) {
  clearTimeout(cachedEntry.idleTimer);

  cachedEntry.idleTimer = setTimeout(async () => {
    await evictCachedPublishChannel(cacheKey);
  }, PUBLISH_CHANNEL_IDLE_TIMEOUT_MS);
}

async function ensurePublishChannel(useConfirmChannel = false) {
  const cacheKey = getCacheKey(useConfirmChannel);
  const existing = publishChannelCache.get(cacheKey);

  if (existing) {
    existing.lastUsedAt = Date.now();
    scheduleIdleEviction(cacheKey, existing);
    return existing.channel;
  }

  const inflightCreation = publishCreationPromises.get(cacheKey);
  if (inflightCreation) {
    return inflightCreation;
  }

  const creationPromise = (async () => {
    const channel = useConfirmChannel
      ? await RMQService.createConfirmChannel()
      : await RMQService.createChannel();

    const cachedEntry = {
      channel,
      lastUsedAt: Date.now(),
      idleTimer: null
    };

    publishChannelCache.set(cacheKey, cachedEntry);
    scheduleIdleEviction(cacheKey, cachedEntry);

    channel.on("close", async () => {
      await evictCachedPublishChannel(cacheKey);
    });

    channel.on("error", async () => {
      await evictCachedPublishChannel(cacheKey);
    });

    return channel;
  })();

  publishCreationPromises.set(cacheKey, creationPromise);

  try {
    return await creationPromise;
  } finally {
    publishCreationPromises.delete(cacheKey);
  }
}

async function produce(exchange, routingKey, message, useConfirmChannel = false) {
  const cacheKey = getCacheKey(useConfirmChannel);
  const channel = await ensurePublishChannel(useConfirmChannel);

  try {
    channel.publish(
      exchange,
      routingKey,
      Buffer.from(JSON.stringify(message))
    );

    const cached = publishChannelCache.get(cacheKey);
    if (cached) {
      cached.lastUsedAt = Date.now();
      scheduleIdleEviction(cacheKey, cached);
    }
  } catch (err) {
    await evictCachedPublishChannel(cacheKey);
    throw err;
  }
}
9. Step-by-Step Walkthrough

How the new flow works

Step 1 — Derive a cache key

We distinguish between standard publish channels and confirm channels. That means the cache is keyed by channel type, not by message.

Step 2 — Reuse if channel already exists

If the right channel is already cached, we simply return it. This avoids unnecessary broker interaction.

Step 3 — Synchronize creation

If multiple publishes arrive concurrently and there is no cached channel yet, only one actual create operation is allowed. The others await the same in-flight promise.

Step 4 — Publish using the shared channel

The message is published using the reused channel, so the publish path becomes lightweight.

Step 5 — Refresh idle timeout

Every time the channel is used, we update lastUsedAt and reset the idle timer.

Step 6 — Cleanup on idle or failure

If the channel becomes idle for too long, or if it emits close/error, it is evicted from cache and closed safely. The next publish recreates it cleanly.

New model: publish A → ensurePublishChannel() → cache miss → create once → cache it → publish publish B → ensurePublishChannel() → cache hit → reuse same channel → publish publish C → ensurePublishChannel() → cache hit → reuse same channel → publish

12. Line-by-Line Explanation

Why the solution is solid engineering, not just a quick patch

publishChannelCache

Stores reusable channels by type. This is the core optimization because it moves us away from per-message lifecycle handling.

publishCreationPromises

Acts like an async lock. It prevents the classic race where 20 concurrent requests all detect a cache miss and each create a channel.

ensurePublishChannel()

Centralizes channel acquisition logic. This is important because it gives one place to handle reuse, creation, locking, and lifecycle.

scheduleIdleEviction()

Ensures channels are not kept forever. This keeps the solution balanced: efficient reuse during load, but cleanup when idle.

channel.on("close") and channel.on("error")

These hooks make the cache self-healing. If the channel becomes invalid, it is removed from cache so the next publish recreates a clean one.

evictCachedPublishChannel()

Cleanup logic is centralized, which avoids duplicated close/delete logic scattered in multiple places.

try/catch around publish

If publish fails, the cached channel is evicted. That protects the system from reusing a broken channel repeatedly.

13. Common Mistakes

What would be easy to get wrong

  • Only caching the channel without synchronization. That still allows a race on first creation under concurrency.
  • Keeping channels forever. Reuse is good, but stale resources still need cleanup.
  • Not evicting on error/close. That can leave a broken channel in cache and cause repeated failures.
  • Fixing only one service locally. The better solution was to fix the shared utility so all consumers benefit.
  • Calling this a RabbitMQ bug. It was an application-side lifecycle design issue, not a broker defect.

15. Design Principles

Patterns and clean code principles demonstrated

Single Responsibility Principle DRY Defensive Programming Resource Pooling Pattern Concurrency Control Centralized Lifecycle Management Self-Healing Resource Cache

SRP

Exchange.produce() no longer directly owns every aspect of channel lifecycle. Lifecycle responsibility is pushed into dedicated helpers such as ensurePublishChannel() and evictCachedPublishChannel().

DRY

Creation, reuse, and cleanup logic are centralized instead of being repeated in multiple branches.

Defensive programming

The code assumes channels can fail or close unexpectedly and handles that explicitly.

Resource pooling

The channel is treated similarly to a pooled DB or HTTP resource: reused while healthy, recreated when invalid, cleaned when idle.

Concurrency control

The async creation lock prevents wasteful duplicate creation under burst traffic.

17. Pattern to Remember

Mental model for future problems

If a resource is expensive to create and cheap to reuse, do not manage it per request/message. Instead: acquire once → reuse safely → clean up on idle/failure

This pattern applies beyond RabbitMQ:

  • Database connections
  • HTTP keep-alive agents
  • Redis clients
  • Thread pools / worker pools
  • AMQP channels
18. Optional Brute Force Comparison

Naive approach vs optimized approach

// ❌ Naive / brute-force style resource handling
async function publishNaive(message) {
  const channel = await RMQService.createChannel();
  channel.publish("XC1-Monitoring", "events", Buffer.from(JSON.stringify(message)));
  await channel.close();
}

// ✅ Optimized reusable resource handling
async function publishOptimized(message) {
  const channel = await ensurePublishChannel(false);
  channel.publish("XC1-Monitoring", "events", Buffer.from(JSON.stringify(message)));
}

The first version is easier to write, but it does not scale. The second version requires a bit more lifecycle logic, but it is much more appropriate for bursty production traffic.
